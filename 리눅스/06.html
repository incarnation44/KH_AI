PART 1. 이론 (4H)

1교시 · 왜 Git인가 (50분)

1.1 Git 없이 프로젝트를 하면

project_final.py
project_final_v2.py
project_final_진짜최종.py
project_final_진짜최종_수정본.py
project_final_이걸로제출.py

여기서 발생하는 문제: - 어느 게 최신인지 모른다 - 어제 잘 되던 버전으로 못 돌아간다 - 4~5명 팀에서 서로 파일을 덮어쓴다 - 누가 뭘 언제 왜 바꿨는지 모른다

1.2 이 과정에서 Git이 갖는 위치 ★

안내서 「교과 1 · 어디로 이어지는가」:

Git/GitHub는 교과 7 이후 모든 프로젝트의 산출물 제출·평가 경로(코드 품질 KPI 측정도구) 로 그대로 쓰임

안내서 「5.3 평가 항목」:

평가 항목 측정 방법 측정 도구
코드 품질 (10) 코드 구조 · 가독성 · 재사용성 및 버전관리 상태 GitHub, 코드 리뷰 체크리스트
프로젝트 수행 역량 (20) 일정 준수 · 협업 참여도 Notion, Git Commit 기록, 발표 평가표

합계 30점이 Git 기록으로 측정됩니다.

안내서 「5.3 운영 포인트」:

여섯 항목 중 세 항목(코드 품질 · 데이터 품질 · 수행 역량, 합계 40점)은 GitHub · Notion · 라벨링 검수표 등 평소 기록물로 측정됩니다. 프로젝트 초반에 기록 규칙을 정해 두면 평가 준비가 함께 진행됩니다.

강사 멘트: "오늘 배우는 건 도구가 아니라, 6개월 뒤 여러분 성적표의 30점입니다."

1.3 Git의 3영역 + 1

 ┌─────────────┐  git add   ┌──────────────┐  git commit  ┌──────────────┐
 │ Working Dir  │──────────▶│ Staging Area  │────────────▶│  Repository   │
 │  (작업 폴더)   │            │   (인덱스)     │              │  (.git 저장소) │
 └─────────────┘◀──────────└──────────────┘◀────────────└──────────────┘
      git restore              git restore --staged           git reset
                                                                   │
                                                          git push │ (7일차)
                                                                   ▼
                                                            ┌─────────────┐
                                                            │Remote(GitHub)│
                                                            └─────────────┘
영역 설명 비유
Working Directory 실제 파일이 있는 폴더 작업대
Staging Area 커밋할 것들을 담아 두는 곳 장바구니
Repository 확정된 이력이 저장된 곳 영수증 보관함

왜 Staging이 있나: 한 번에 10개 파일을 수정했어도, 관련된 3개만 골라 하나의 의미 있는 커밋으로 만들 수 있습니다. 의미 단위 커밋의 기반입니다.

1.4 파일의 상태

Untracked ──git add──▶ Staged ──git commit──▶ Committed(Unmodified)
                          ▲                         │
                          │                    파일 수정
                          └────git add──── Modified ◀┘

git status              # 현재 상태 확인 (가장 자주 쓰는 명령)
git status -s           # 짧게

2교시 · 기본 워크플로우 (50분)

2.1 초기 설정 (최초 1회)

git config --global user.name  "홍길동"
git config --global user.email "hong@example.com"
git config --global core.editor "vim"        # 또는 nano
git config --global init.defaultBranch main
git config --global core.autocrlf input      # 리눅스/맥
git config --global core.quotepath false     # 한글 파일명 깨짐 방지 ★
git config --list

core.quotepath false 를 안 하면 한글 파일명이 \355\225\234\352\270\200 처럼 보입니다.

2.2 저장소 시작

git init                 # 현재 폴더를 저장소로
ls -a                    # .git 폴더 생성 확인
git status

2.3 add / commit

git add 파일명
git add .                # 현재 폴더 이하 전부
git add *.sh             # 패턴
git add -p               # 변경 조각(hunk) 단위 선택 ★고급

git commit -m "메시지"
git commit               # 편집기 열림 (여러 줄 메시지)
git commit -am "메시지"  # 추적 중인 파일 add+commit (신규 파일은 안 됨)
git commit --amend       # 직전 커밋 수정 ⚠️ push 후엔 금지

2.4 이력 조회

git log
git log --oneline                       # 한 줄로
git log --oneline --graph --all         # 그래프 ★
git log -3                              # 최근 3개
git log --stat                          # 변경 파일 통계
git log -p                              # 변경 내용 포함
git log --author="홍길동"
git log --since="2 days ago"
git log --oneline -- scripts/           # 특정 경로 이력

git show <해시>                          # 특정 커밋 상세
git diff                                # 작업폴더 vs 스테이징
git diff --staged                       # 스테이징 vs 최근커밋
git diff HEAD                           # 작업폴더 vs 최근커밋
git diff <해시1> <해시2>

2.5 되돌리기 — 3단계 구분 ★

상황 명령 위험도
작업 폴더 수정 취소 git restore 파일 중 (변경 소실)
스테이징 취소 git restore --staged 파일 낮음
직전 커밋 취소(변경 유지) git reset --soft HEAD~1 낮음
직전 커밋 취소(스테이징도 해제) git reset HEAD~1 낮음
직전 커밋 완전 삭제 git reset --hard HEAD~1 높음 ⚠️
커밋 되돌리는 새 커밋 생성 git revert <해시> 낮음 (공유 이력에는 이것) 
git reflog              # 모든 HEAD 이동 기록 — reset 사고 시 구조선 ★

철칙: 이미 push한 커밋은 reset 대신 revert. reset --hard 후 push하면 팀원의 이력이 깨집니다.

2.6 .gitignore

# 패턴 규칙
*.pt              # 확장자
logs/             # 디렉토리
/build            # 루트의 build만
!important.pt     # 예외(무시하지 않음)
**/temp           # 모든 깊이의 temp

git check-ignore -v 파일명       # 어느 규칙에 걸렸는지 확인 ★
git rm --cached 파일명           # 이미 추적 중인 파일 제외
git status --ignored             # 무시된 파일 표시

⚠️ .gitignore는 이미 추적 중인 파일에는 소용없습니다. 실수로 커밋한 이미지는 git rm --cached로 빼야 합니다. 그래도 이력에는 남습니다 → 7일차에서 다룹니다.

3교시 · 커밋 메시지와 브랜치 (50분)

3.1 좋은 커밋 = 좋은 점수

나쁜 예

수정
ㅁㄴㅇㄹ
final
update
작업

좋은 예 (Conventional Commits)

feat(dataset): 이미지-라벨 정합성 검증 기능 추가
fix(split): 시드 고정 시 재현되지 않던 버그 수정
docs(readme): 설치 절차 및 실행 예시 보강
refactor(check): 검증 로직을 함수 단위로 분리

3.2 Conventional Commits 규격

<type>(<scope>): <subject>

<body>

<footer>
type 용도
feat 새 기능
fix 버그 수정
docs 문서
style 포맷팅(로직 변경 없음)
refactor 리팩터링
test 테스트
chore 빌드·설정·잡무
data (본 과정 추가) 데이터셋 구성 변경

subject 규칙 - 50자 이내 - 명령형 또는 명사형 (한국어는 "~추가", "~수정") - 마침표 없음 - 무엇을 왜 바꿨는지가 드러날 것

3.3 커밋 단위 — 실무 기준

원칙 설명
하나의 커밋 = 하나의 논리적 변경 기능 추가와 오타 수정을 섞지 않음
되돌릴 수 있는 단위 이 커밋만 취소해도 말이 되는가?
커밋 후 항상 동작 깨진 상태를 커밋하지 않음
너무 크지도 작지도 파일 1~5개, 변경 200줄 이내 권장

평가 관점: 심사자가 git log --oneline을 봤을 때 프로젝트의 진행 과정이 이야기로 읽히면 만점, 수정만 50줄이면 감점입니다.

3.4 브랜치

git branch                       # 목록
git branch <이름>                 # 생성
git switch <이름>                 # 이동 (신버전)
git checkout <이름>               # 이동 (구버전)
git switch -c <이름>              # 생성+이동 ★
git branch -d <이름>              # 삭제 (머지된 것만)
git branch -D <이름>              # 강제 삭제
git branch -m 새이름              # 이름 변경

3.5 머지

git switch main
git merge feature/dataset-check

Fast-forward vs 3-way merge

[FF] main이 뒤처져 있고 갈라지지 않은 경우 — 포인터만 이동
main:    A---B
feature:      \---C---D    →  main: A---B---C---D

[3-way] 양쪽이 각각 진행된 경우 — 머지 커밋 생성
main:    A---B---E
feature:      \---C---D    →  main: A---B---E---M
                                          \---C---D---/

git merge --no-ff feature/x     # 항상 머지 커밋 생성 (이력이 명확)

3.6 충돌(Conflict)

같은 파일의 같은 줄을 양쪽에서 다르게 고치면 발생합니다.

<<<<<<< HEAD
MIN_IMAGES=500
=======
MIN_IMAGES=1000
>>>>>>> feature/threshold

해결 절차 1. git status 로 충돌 파일 확인 2. 편집기로 열어 <<<<<<<, =======, >>>>>>> 를 모두 제거하고 원하는 내용만 남김 3. git add 파일 4. git commit (메시지 자동 제안됨)

git merge --abort         # 머지 취소하고 이전 상태로

3.7 태그

git tag v1.0
git tag -a v1.0 -m "교과1 최종 산출물"
git tag
git show v1.0

프로젝트 마일스톤(중간발표, 최종발표)마다 태그를 달아 두면 심사자가 특정 시점을 바로 확인할 수 있습니다.

4교시 (전반) · 브랜치 전략과 팀 규칙 (30분)

4.1 본 과정 권장 브랜치 전략 (GitHub Flow 단순화)

main            ●───●───────●───────●        항상 동작하는 상태
                 \         /       /
feature/xxx       ●───●───●       /          기능 단위 작업
                                 /
fix/yyy                    ●────●            버그 수정
브랜치 명명 규칙 용도
main — 항상 배포/시연 가능한 상태
feature/<기능> feature/label-tool 새 기능
fix/<버그> fix/split-seed 버그 수정
docs/<문서> docs/readme 문서

규칙 1. main에 직접 커밋 금지 (7일차 PR로 강제) 2. 브랜치는 짧게 유지 (1~3일 내 머지) 3. 머지 전 main을 최신으로 받아 충돌 미리 해결

4.2 팀 프로젝트 대비 (교과 14·15 예고)

안내서 교과 14 운영 포인트:

팀 구성은 4~5명이며 팀장과 역할을 구분합니다. 산출물은 수행계획서 · UML · 데이터 정의서 · 설계산출물 · 테스트산출물 · 최종제품 및 성능보고서

4~5명이 동시에 코드를 고칩니다. 브랜치 전략이 없으면 매일 충돌합니다.

실습 6-1 · 저장소 시작과 첫 커밋 (50분)

Step 1. 설정

git config --global user.name  "본인이름"
git config --global user.email "본인이메일"
git config --global core.editor "vim"
git config --global init.defaultBranch main
git config --global core.quotepath false
git config --global alias.st status
git config --global alias.lg "log --oneline --graph --all --decorate"
git config --list | grep -E "user|alias"

Step 2. 저장소 초기화

cd ~/kdt-linux
git init
git status
ls -a

Step 3. .gitignore 먼저 확인 ★

cat .gitignore                 # 5일차에 만든 것
git status                     # 이미지가 안 보이는지 확인
git status --ignored | head -20

순서가 중요합니다. .gitignore 없이 git add . 를 하면 이미지 999장이 스테이징됩니다. 그리고 그건 이력에 영구히 남습니다.

Step 4. 첫 커밋

git add .gitignore
git status
git commit -m "chore: 프로젝트 초기 .gitignore 추가"
git log

Step 5. 의미 단위 커밋 연습 ★

한 번에 git add . 하지 않고, 주제별로 나눠서 커밋합니다.

# 커밋 2: 스크립트
git add scripts/dataset_check.sh
git commit -m "feat(check): 데이터셋 정합성 검증 스크립트 추가

- 이미지-라벨 짝 검증
- 빈 라벨/필드수/좌표범위/클래스ID 검사
- --fix 자동 수정, --min 최소 장수 옵션
- 종료코드 0(PASS)/1(FAIL)/2(사용법)"

# 커밋 3: 분할 스크립트
git add scripts/split_dataset.sh
git commit -m "feat(split): 시드 고정 재현 가능한 데이터셋 분할 스크립트 추가"

# 커밋 4: 백업/파이프라인
git add scripts/auto_backup.sh scripts/run_pipeline.sh scripts/list_datasets.sh
git commit -m "feat(ops): 백업 및 통합 파이프라인 스크립트 추가"

# 커밋 5: 환경
git add env/
git commit -m "chore(env): conda 환경 정의 파일 추가"

실습 6-2 · 수정·조회·되돌리기 (60분)

Step 1. 수정과 diff

# MIN_IMAGES=500 → MIN_IMAGES=300 으로 변경 후 저장

git diff 출력 읽기:

-MIN_IMAGES=500        ← 빨강 / - : 삭제된 줄
+MIN_IMAGES=300        ← 초록 / + : 추가된 줄

Step 2. 스테이징과 diff의 차이

git add scripts/dataset_check.sh
git diff                       # 아무것도 안 나옴 (작업폴더 = 스테이징)
git diff --staged              # 여기서 보임
git status -s                  # M 이 왼쪽 열에 표시

Step 3. 되돌리기 3단계 실습 ★

① 작업 폴더 수정 취소

git restore --staged scripts/dataset_check.sh   # 먼저 언스테이징
git status
git restore scripts/dataset_check.sh            # 수정 취소
grep "MIN_IMAGES=" scripts/dataset_check.sh     # 500 으로 복원 확인

② 커밋 취소 (변경은 유지)

echo "# 임시 메모" >> scripts/dataset_check.sh
git add . && git commit -m "temp: 임시 커밋"
git log --oneline -3

git reset --soft HEAD~1        # 커밋만 취소, 스테이징 유지
git status                     # 스테이징 상태
git log --oneline -3

git reset HEAD~0               # (mixed) 스테이징 해제
git restore scripts/dataset_check.sh

③ reflog로 구조 (사고 복구) ★

echo "실수" >> DAY5.md
git add . && git commit -m "temp: 실수 커밋"
HASH=$(git rev-parse HEAD)
echo "이 해시를 기억: $HASH"

git reset --hard HEAD~1        # ⚠️ 커밋 완전 삭제
git log --oneline -3           # 사라짐

git reflog                     # 모든 이동 기록에는 남아 있음 ★
git reset --hard $HASH         # 복구
git log --oneline -3           # 돌아옴

# 정리
git reset --hard HEAD~1
git restore DAY5.md 2>/dev/null || true

git reflog 는 Git의 안전망입니다. reset --hard 로 날린 커밋도 기본 90일간 복구 가능합니다. 이걸 모르면 사고 시 프로젝트를 통째로 잃습니다.

실습 6-3 · .gitignore 실전 (40분)

Step 1. 실수 재현 — 이미지를 커밋해 보기

cd ~/kdt-linux
mkdir -p tmp_test
cp dataset/kimchi/raw/images/kimchi_0001.jpg tmp_test/ 2>/dev/null || \
  cp dataset/kimchi/raw/kimchi_0001.jpg tmp_test/

git status                     # .gitignore의 *.jpg 규칙에 걸려 안 보임
git check-ignore -v tmp_test/kimchi_0001.jpg     # 어느 규칙인지 확인 ★

git add -f tmp_test/kimchi_0001.jpg              # 강제 추가 (실수 재현)
git status
git commit -m "chore: 실수로 이미지 커밋"
git log --stat -1

Step 2. 되돌리기

git rm --cached tmp_test/kimchi_0001.jpg
git commit -m "fix: 실수로 커밋된 이미지 제거"
git status

# 그러나 이력에는 여전히 남아 있음 ★
git log --all --oneline -- "*.jpg"
git show HEAD~1 --stat

⚠️ 핵심 교훈: git rm --cached 는 앞으로만 제외할 뿐, 과거 이력에서는 지워지지 않습니다. ㈜비솔 실데이터를 실수로 커밋하면 git rm --cached 로 해결되지 않고, 이력 재작성(git filter-repo) 또는 저장소 폐기가 필요합니다. → 7일차에 이를 원천 차단하는 pre-commit 훅을 만듭니다.

rm -rf tmp_test
git add . && git commit -m "chore: 테스트 파일 정리" 2>/dev/null || true

Step 3. .gitignore 규칙 실험

mkdir -p ignore_test && cd ignore_test
touch a.jpg b.pt c.log d.md
mkdir sub && touch sub/e.jpg

cat > .gitignore << 'EOF'
*.jpg
*.pt
*.log
!important.log
EOF

touch important.log
cd ~/kdt-linux
git status --short ignore_test/
git check-ignore -v ignore_test/a.jpg
git check-ignore -v ignore_test/sub/e.jpg
git check-ignore -v ignore_test/important.log ; echo "exit=$?"

rm -rf ignore_test

Step 4. 최종 .gitignore 정비

cd ~/kdt-linux
cat >> .gitignore << 'EOF'

*.pem
*.key
.env

aws_credentials

check_volume() 함수 아래에 추가:

check_resolution () {
    section 7 "이미지 해상도"
    local raw="$DATASET_DIR/raw"
    if ! command -v identify > /dev/null 2>&1; then
        warn "ImageMagick 미설치 - 해상도 검증 생략"
        return
    fi
    local small
    small=$(find "$raw" -name "*.jpg" | head -100 | while read -r f; do
        identify -format "%w %h\n" "$f" 2>/dev/null
    done | awk '$1<640 || $2<640 {c++} END {print c+0}')
    if [ "$small" -eq 0 ]; then ok "해상도 640 이상"
    else warn "640 미만 이미지 ${small}건 (샘플 100장 기준)"; fi
}

main() 안 show_distribution 앞에 check_resolution 호출 추가.
