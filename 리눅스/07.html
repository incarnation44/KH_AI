PART 1. 이론 (3.5H)

1교시 · 원격 저장소 (50분)

1.1 Git ≠ GitHub

Git GitHub
버전관리 도구 Git 저장소 호스팅 서비스
로컬에서 동작 웹 기반, 협업 기능 제공
오프라인 가능 Issue, PR, Actions, Wiki

대안: GitLab, Bitbucket, Gitea(사내 설치형). 안내서에 GitHub가 명시되어 있으므로 GitHub를 사용합니다.

1.2 원격 저장소 명령

git remote -v                                  # 원격 목록
git remote add origin <URL>                    # 원격 추가
git remote set-url origin <새URL>
git remote remove origin

git clone <URL>                                # 복제
git clone <URL> <폴더명>
git clone --depth 1 <URL>                      # 최근 1개 커밋만 (빠름)

git push -u origin main                        # 최초 push (-u: 추적 설정)
git push                                        # 이후
git push origin <브랜치>
git push --tags                                 # 태그 전송

git fetch origin                                # 원격 변경 가져오기(머지 안 함)
git pull                                        # fetch + merge
git pull --rebase                               # fetch + rebase (이력 깔끔)

1.3 fetch vs pull ★

fetch:  원격 변경사항을 로컬에 "가져오기만" → 내가 확인 후 머지 결정
pull:   가져와서 "바로 머지"

git fetch origin
git log --oneline HEAD..origin/main       # 원격에만 있는 커밋 확인
git diff HEAD origin/main                  # 무엇이 다른가
git merge origin/main                      # 확인 후 머지

팀 작업 권장: pull 대신 fetch → 확인 → merge. 무엇이 들어오는지 모르고 머지하면 충돌 대응이 어렵습니다.

1.4 인증 방식

방식 특징
HTTPS + PAT 토큰 발급 필요, 만료 관리, 방화벽 친화적
SSH 키 최초 설정 후 편함, 22번 포트 필요

사내망에서 22번 포트가 막혀 있으면 SSH가 안 됩니다. 교실 환경에 따라 강사가 사전 확인하십시오. HTTPS+PAT는 443 포트를 쓰므로 대부분 통과합니다.

SSH 키 생성

ssh-keygen -t ed25519 -C "hong@example.com"
# 저장 경로: 기본(~/.ssh/id_ed25519), 패스프레이즈: 선택

cat ~/.ssh/id_ed25519.pub                  # 공개키 (GitHub에 등록)
chmod 600 ~/.ssh/id_ed25519                # 개인키 권한 ★ 2일차 내용

ssh -T git@github.com                       # 연결 테스트

PAT 발급 GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate - scope: repo 체크 - 발급된 토큰은 한 번만 표시됩니다. 안전한 곳에 보관.

git config --global credential.helper store    # 저장 (평문 ⚠️)
git config --global credential.helper cache --timeout=3600   # 권장

2교시 · 협업 워크플로우 (50분)

2.1 GitHub Flow

1. main에서 브랜치 생성        git switch -c feature/xxx
2. 작업 + 커밋                  git commit
3. 원격에 push                  git push -u origin feature/xxx
4. Pull Request 생성            (GitHub 웹)
5. 코드 리뷰 + 수정             (리뷰어 코멘트 → 추가 커밋)
6. Approve → Merge              (GitHub 웹)
7. 브랜치 삭제 + 로컬 동기화    git switch main && git pull && git branch -d

2.2 Pull Request가 하는 일

기능 의미
변경 내역 시각화 무엇이 바뀌는지 라인 단위로 보임
코드 리뷰 라인별 코멘트, 수정 제안
자동 검사 CI (Actions)로 문법·테스트 자동 실행
이력 보존 왜 이렇게 바꿨는지 논의가 남음
머지 게이트 승인 없이는 main에 못 들어감

평가 연계: 안내서 평가항목 「코드 품질 — 코드 리뷰 체크리스트」, 「수행 역량 — 협업 참여도」가 PR 활동으로 측정됩니다. 리뷰 코멘트를 성실히 주고받은 기록이 점수입니다.

2.4 코드 리뷰 규칙 (본 과정 팀 규칙)

3.1 반드시 지켜야 할 규정

안내서 6.2절 · 7장:

2026.08 확정 — ㈜비솔 제공 데이터의 사용 범위가 확정되었습니다. 원내 폐쇄망에서만 실습·프로젝트 개발 용도로 사용하며, 외부 클라우드 및 GitHub 업로드는 금지됩니다. 결과 화면·시연 영상 및 포트폴리오 활용은 가능하고, 외부 반출은 금지되며 훈련생 개인별 보안서약서를 징구합니다.

데이터 GitHub 업로드
㈜비솔 제공 조각김치·이물 이미지 + 라벨 (교과 8) ❌ 금지

코드·스크립트·메타 문서 ✅ 가능
결과 화면·시연 영상 ✅ 가능

3.2 왜 .gitignore 만으로는 부족한가

6일차에 확인한 사실: 1. git add -f 로 강제 추가하면 무시 규칙이 뚫린다 2. .gitignore 는 이미 추적 중인 파일에 소용없다 3. 한 번 커밋되면 git rm --cached 해도 이력에는 남는다 4. push 되면 GitHub 서버에 영구 기록된다

결론: 사람의 주의력에 의존하면 반드시 사고가 납니다.

3.3 방어선 3중 구조

① .gitignore              — 실수 방지 (기본)
② pre-commit 훅           — 커밋 자체를 차단 (핵심) ★
③ GitHub Actions (CI)     — push 후 검사 및 알림

3.4 Git 훅

.git/hooks/ 에 실행 가능한 스크립트를 두면 특정 시점에 자동 실행됩니다.

훅 실행 시점
pre-commit 커밋 직전 (0이 아니면 커밋 중단) ★
commit-msg 메시지 작성 후 (형식 검사)
pre-push push 직전

⚠️ .git/hooks/ 는 Git으로 추적되지 않습니다. 팀 공유하려면 hooks/ 폴더에 두고 설치 스크립트를 제공하거나, core.hooksPath 를 설정합니다.

3.5 Git LFS

100MB 이상 파일은 GitHub가 거부합니다. 모델 가중치(.pt, .onnx, .engine)가 여기 해당합니다.

git lfs install
git lfs track "*.pt"
git add .gitattributes
git lfs ls-files

본 과정 권장: 모델 가중치는 LFS보다 GitHub Releases 또는 별도 저장소를 권장합니다. LFS는 무료 할당량(1GB/월 대역폭)이 금방 소진됩니다.

3.6 GitHub Actions 맛보기

.github/workflows/*.yml 에 정의하면 push/PR 시 자동 실행됩니다.

name: CI
on: [push, pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Shell syntax check
        run: |
          for f in scripts/*.sh; do bash -n "$f"; done

교과 14 팀별 차별화 기능 중 MLOps 가 가산 평가 대상입니다(안내서 교과 14 운영 포인트). CI 파이프라인 구축이 그 출발점입니다.

실습 7-2 · pre-commit 보안 훅 (60분) ★★핵심

배경

안내서 6.2절 규정을 기술적으로 강제하는 장치를 만듭니다. 이 훅은 교과 8·14·15 프로젝트 저장소에 그대로 복사해 사용합니다.

요구 기능

# 차단 대상
B1 이미지·동영상 파일 (jpg/png/mp4 등)
B2 모델 가중치 (pt/pth/onnx/engine/tflite)
B3 대용량 파일 (10MB 초과)
B4 자격증명 (pem/key/.env/credentials)
B5 기업 데이터 경로 (dataset/*/raw/)
B6 커밋 메시지 형식 검사 (별도 훅)

Step 1. 훅 스크립트 작성

mkdir -p ~/kdt-linux/hooks
cd ~/kdt-linux/hooks
vim pre-commit

#!/bin/bash
#===============================================================
# pre-commit hook
# 목적: ㈜비솔 제공 데이터 및 대용량/민감 파일의 커밋을 차단
# 근거: AI캠퍼스 훈련운영 안내서 6.2절 · 7장 데이터 보안 규정
#===============================================================
set -uo pipefail

RED='\033[0;31m'; YEL='\033[0;33m'; GRN='\033[0;32m'; NC='\033[0m'
BLOCKED=0
MAX_SIZE=$((10 * 1024 * 1024))     # 10MB

STAGED=$(git diff --cached --name-only --diff-filter=ACM)
[ -z "$STAGED" ] && exit 0

block () {
    echo -e "${RED}  ✘ BLOCKED${NC} $1"
    echo -e "    이유: $2"
    BLOCKED=1
}

echo "─────────────────────────────────────────────"
echo " pre-commit 보안 검사"
echo "─────────────────────────────────────────────"

while IFS= read -r file; do
    [ -f "$file" ] || continue

    # B1. 이미지 / 동영상
    case "$file" in
        *.jpg|*.jpeg|*.png|*.bmp|*.gif|*.tif|*.tiff|*.webp|*.mp4|*.avi|*.mov|*.mkv)
            block "$file" "이미지·영상 파일은 저장소에 포함할 수 없습니다 (데이터 보안 규정)"
            continue ;;
    esac

    # B2. 모델 가중치
    case "$file" in
        *.pt|*.pth|*.onnx|*.engine|*.tflite|*.h5|*.pb|*.caffemodel)
            block "$file" "모델 가중치는 Releases 또는 별도 저장소를 사용하세요"
            continue ;;
    esac

    # B4. 자격증명
    case "$file" in
        *.pem|*.key|*.p12|.env|*credentials*|*secret*|*token*)
            block "$file" "자격증명 파일은 절대 커밋할 수 없습니다"
            continue ;;
    esac

    # B5. 기업 데이터 경로
    case "$file" in
        */raw/*|dataset/*/raw/*|*/processed/*)
            block "$file" "원본·전처리 데이터 경로는 커밋 대상이 아닙니다"
            continue ;;
    esac

    # B3. 대용량
    size=$(stat -c%s "$file" 2>/dev/null || echo 0)
    if [ "$size" -gt "$MAX_SIZE" ]; then
        block "$file" "파일 크기 $((size/1024/1024))MB > 10MB 제한"
        continue
    fi

    # 하드코딩된 비밀정보 스캔 (경고)
    if grep -qEi "(aws_secret|api[_-]?key|password\s*=\s*['\"])" "$file" 2>/dev/null; then
        echo -e "${YEL}  ⚠ WARN${NC}    $file"
        echo    "    비밀정보로 보이는 문자열이 있습니다. 확인하세요."
    fi

done <<< "$STAGED"

echo "─────────────────────────────────────────────"
if [ "$BLOCKED" -eq 1 ]; then

#!/bin/bash
# commit-msg hook — Conventional Commits 형식 검사
MSG_FILE="$1"
MSG=$(head -1 "$MSG_FILE")

# merge/revert 커밋은 통과
echo "$MSG" | grep -qE "^(Merge|Revert)" && exit 0

PATTERN="^(feat|fix|docs|style|refactor|test|chore|data|merge)(\([a-z0-9_-]+\))?: .{5,72}$"

if ! echo "$MSG" | grep -qE "$PATTERN"; then
    echo ""
    echo "✘ 커밋 메시지 형식이 올바르지 않습니다."
    echo ""
    echo "  현재: $MSG"
    echo ""
    echo "  형식: <type>(<scope>): <subject>"
    echo "  type: feat|fix|docs|style|refactor|test|chore|data"
    echo "  예시: feat(check): 해상도 검증 기능 추가"
    echo ""
    exit 1
fi
exit 0

check_balance () {
    section 8 "클래스 균형"
    local raw="$DATASET_DIR/raw"
    local stats
    stats=$(cat "$raw"/labels/*.txt "$raw"/*.txt 2>/dev/null \
            | cut -d' ' -f1 | sort | uniq -c | awk '{print $1}' | sort -n)
    local min max ratio
    min=$(echo "$stats" | head -1)
    max=$(echo "$stats" | tail -1)
    [ -z "$min" ] && { log "(라벨 없음)"; return; }
    ratio=$(awk -v a="$max" -v b="$min" 'BEGIN{printf "%.1f", a/b}')
    log "최다/최소 클래스 비율: ${ratio}:1 (max=$max, min=$min)"
    if awk -v r="$ratio" 'BEGIN{exit !(r>5)}'; then
        warn "클래스 불균형 심함 (5:1 초과) — 증강 또는 가중 손실 검토 필요"

마무리 (10분)

cd ~/kdt-linux
git tag -a v2.0-day7 -m "교과1 7일차 — GitHub 협업 및 보안 체계 완료"
git push --tags

cat > DAY7.md << 'EOF'
# Day 7 — GitHub 협업 · 데이터 보안
## 핵심
- SSH 키 / PAT 인증, remote add / push -u
- fetch → 확인 → merge (pull보다 안전)
- GitHub Flow: branch → push → PR → review → merge → delete
- 리뷰 접두사: [must] [should] [nit] [q] [praise]
- 3중 방어선: .gitignore → pre-commit 훅 → GitHub Actions
## 보안 규정 (안내서 6.2절·7장)
- ㈜비솔 제공 데이터: 원내 폐쇄망 전용, GitHub 업로드 금지
- 훈련생 직접 촬영(교과 14): 외부 반출 가능
EOF
git add DAY7.md && git commit -m "docs: 7일차 학습 정리" && git push

과제 (8일차 프로젝트 준비)

  1. 오늘 만든 저장소를 정리하고, 8일차 파이널 프로젝트 계획을 Issue로 등록
  2. git stash, git rebase -i, git cherry-pick 중 하나를 조사해 사용 시나리오 작성
  3. 팀원의 저장소를 clone해서 README만 보고 실행이 되는지 검증 → 안 되면 Issue 등록
  4. 8일차 프로젝트 요구사항 문서(08_8일차_부분파이널프로젝트_visionops.md) 정독

강사 운영 노트

시점 주의사항
SSH 포트 개강 전 반드시 22번 포트 개방 여부를 확인하십시오. 막혀 있으면 30명이 동시에 막힙니다. HTTPS+PAT 대안을 준비해 두십시오.
Private 저장소 반드시 Private로 만들게 하십시오. Public에 실수로 올라가면 회수가 불가능합니다.
pre-commit 훅 오늘의 하이라이트입니다. 안내서 보안 규정과 직접 연결되므로, 규정 원문을 화면에 띄우고 시작하십시오. 훅이 실제로 차단되는 장면을 전원이 봐야 합니다.
PR 실습 2인 1조 편성 시 전공/비전공을 섞으십시오. 리뷰 과정에서 자연스러운 상호 학습이 일어납니다.
역할 교대 리뷰어 경험이 없으면 교과 14·15 팀 프로젝트에서 리뷰가 형식화됩니다. 반드시 양쪽을 경험시키십시오.
Actions 무료 사용량 제한이 있습니다. 30명 × 여러 push면 Private 저장소 분(minutes)이 소진될 수 있으니, 워크플로우를 가볍게 유지하십시오.
시간 부족 7-4(Issue/Actions)를 축소하고 7-3(PR 사이클)을 반드시 완주시키십시오.
