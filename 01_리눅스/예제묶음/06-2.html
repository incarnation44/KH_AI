명령어 연습 부록 — add/commit · log · 되돌리기 · branch/merge 각 20제

쉬운 예제 10개 → 어려운 예제 10개 순서로, Git 명령이 손에 익도록 반복 연습합니다

이 문서의 목표: D6에서 배운 Git 명령이 "낯선 도구"에서 "손에 익은 습관"이 되도록, 아주 쉬운 예제부터 실무에 가까운 예제까지 단계적으로 반복 연습합니다.

이 문서를 보는 법

  • 각 명령어마다 쉬움 10개 → 어려움 10개 순서로 배치되어 있습니다. 쉬움부터 순서대로 직접 타이핑해 보세요.
  • $로 시작하는 줄이 "내가 입력하는 명령"이고, 그 아래 줄이 예상 결과입니다. 커밋 해시(예: a1b2c3d)는 실습마다 다르게 나오므로 예시와 똑같지 않아도 정상입니다.
  • 각 예제 아래 의미가 "이 명령이 왜 이렇게 동작하는지"를 설명합니다.
  • 이 문서는 실제로 만들고 있는 프로젝트 저장소와는 별개의 연습용 저장소에서 진행합니다. 마음껏 커밋하고, 되돌리고, 브랜치를 만들었다 지워도 괜찮습니다.
  • 막히면 D6 본문(06.html)의 해당 절로 돌아가 개념을 다시 확인하세요.

실습 준비 — 연습용 저장소 만들기

mkdir -p ~/kdt-linux/git-practice && cd ~/kdt-linux/git-practice
git init
git config user.name "kdt-student"
git config user.email "kdt@example.com"

echo "안녕하세요" > note.txt

예상 결과: Initialized empty Git repository in .../git-practice/.git/ 메시지와 함께 빈 저장소가 만들어지고, note.txt 파일 하나가 준비됩니다.

1. add / commit — 변경사항을 저장하기

add는 "이번에 저장할 내용을 준비 영역에 올리는 것", commit은 "그 준비된 내용을 하나의 저장 시점으로 확정하는 것"입니다.

add/commit · 쉬움 10제

  1. $ git status
On branch main
No commits yet
Untracked files:
  (use "git add ..." to include in what will be committed)
        note.txt

    의미: 지금 폴더의 파일이 git에 아직 추적되지 않고 있음(Untracked)을 보여줍니다. commit 전 항상 먼저 확인하는 명령입니다.

  2. $ git add note.txt
(출력 없음 — 다시 git status 하면 "Changes to be committed"에 note.txt가 보임)

    의미: 파일을 "다음 커밋에 포함시킬 준비 영역(스테이징)"에 올립니다.

  3. $ git commit -m "docs: 첫 메모 추가"
[main (root-commit) a1b2c3d] docs: 첫 메모 추가
 1 file changed, 1 insertion(+)
 create mode 100644 note.txt

    의미: 스테이징된 내용을 하나의 "저장 시점(커밋)"으로 기록합니다. -m 뒤에 메시지를 바로 씁니다.

  4. $ echo "두번째 줄" >> note.txt
$ git add .
(폴더 안의 변경된 모든 파일이 스테이징됨)

    의미: 파일명 대신 .(현재 폴더)을 쓰면 변경된 모든 파일을 한 번에 추가합니다.

  5. $ git add *.txt
(.txt로 끝나는 파일들만 스테이징됨)

    의미: 와일드카드로 특정 확장자만 골라 추가할 수 있습니다.

  6. $ echo "세번째 줄" >> note.txt
$ git commit -am "docs: 세번째 줄 추가"
(add 없이 바로 커밋됨 — note.txt는 이미 git이 추적 중이므로)

    의미: -a는 "이미 git이 알고 있는 파일"의 수정사항을 자동으로 스테이징한 뒤 커밋까지 한 번에 처리합니다(새 파일은 포함되지 않습니다).

  7. $ echo "네번째 줄" >> note.txt && touch new.txt
$ git status -s
 M note.txt
?? new.txt

    의미: -s(short)는 각 파일 앞에 M(수정)/??(추적 안 됨) 같은 기호로 상태를 간단히 보여줍니다.

  8. $ git add -A
(새 파일, 수정된 파일, 삭제된 파일까지 전부 스테이징됨)

    의미: -A(all)는 git add .보다 더 넓은 범위(삭제된 파일 포함)를 반영합니다.

  9. $ git commit -m "네번째 줄"
$ git commit --amend -m "docs: 네번째 줄 추가 및 new.txt 생성"
(방금 한 커밋의 메시지가 새 메시지로 교체됨)

    의미: --amend는 "방금 커밋에 뭔가 빠뜨렸거나 메시지를 잘못 썼을 때" 그 커밋 자체를 고치는 명령입니다.

  10. $ echo "다섯번째" >> note.txt && echo "메모" > memo.txt
$ git add note.txt memo.txt
(두 파일이 함께 스테이징됨)

    의미: add 뒤에 여러 파일명을 공백으로 나열하면 한 번에 여러 개를 추가합니다.

add/commit · 어려움 10제

  1. $ git add -p
diff --git a/note.txt b/note.txt
...
Stage this hunk [y,n,q,a,d,s,e,?]?

    의미: 한 파일 안에서도 변경 덩어리(hunk)별로 "이 부분만 커밋하고 저 부분은 나중에" 나눌 수 있습니다 — 의미 단위 커밋의 핵심 도구입니다.

  2. $ git commit --no-verify -m "긴급 수정"
(pre-commit 훅 검사를 건너뛰고 강제로 커밋 진행)

    의미: 커밋 전 자동 검사(훅)가 걸려있을 때, 예외적으로 그 검사를 생략하고 커밋합니다(남용하면 안 됩니다).

  3. $ git commit --allow-empty -m "체크포인트"
[main 9f8e7d6] 체크포인트

    의미: 아무 파일 변경이 없어도 빈 커밋이 하나 생성됩니다. 코드 변경 없이 "이 시점을 표시"만 하고 싶을 때(예: CI 트리거) 쓰는 특수 커밋입니다.

  4. $ GIT_AUTHOR_DATE="2026-01-01T09:00:00" git commit -m "과거 날짜로 기록"
(커밋 시각이 지정한 과거 날짜로 기록됨)

    의미: 환경변수로 커밋 시각을 직접 지정할 수 있습니다(데이터 이관·복원 시나리오에서 가끔 필요합니다).

  5. $ git add . -- ':!*.jpg'
(.jpg 파일만 제외한 나머지 변경사항이 전부 스테이징됨)

    의미: pathspec의 제외 패턴(:!)으로 "이것만 빼고 전부"를 표현할 수 있습니다. 이미지 실수 커밋을 방지하는 안전한 습관입니다.

  6. $ git add note.txt
$ git diff --cached
diff --git a/note.txt b/note.txt
+다섯번째

    의미: 커밋하기 직전, "정확히 무엇이 이번 커밋에 들어가는지" 최종 확인하는 명령입니다.

  7. $ echo "fix: 로그인 오류 수정

세션 만료 시 자동 로그아웃되지 않던 문제를 고쳤습니다." > commit_message.txt
$ git commit -m "$(cat commit_message.txt)"
(파일에 미리 써둔 긴 커밋 메시지가 그대로 사용됨)

    의미: 커밋 메시지가 여러 줄로 길어질 때, 파일로 작성해두고 명령치환으로 불러오면 따옴표 문제 없이 깔끔합니다.

  8. $ git commit -m "fix: 버그 수정" -m "상세 설명은 여기에 적습니다"
[main 1a2b3c4] fix: 버그 수정

    의미: -m을 두 번 쓰면 "제목 한 줄 + 빈 줄 + 본문"이라는 Git 권장 커밋 메시지 형식을 명령줄에서 바로 만들 수 있습니다.

  9. $ echo "API_KEY=12345" > secret.env
$ git add secret.env && git commit -m "실수로 추가"
$ git rm --cached secret.env
rm 'secret.env'

    의미: --cached는 파일은 폴더에 그대로 남기되, 앞으로의 git 추적 대상에서만 뺍니다. 실수로 커밋했던 민감 파일을 정리할 때 .gitignore와 함께 사용합니다.

  10. $ git status --porcelain
 M note.txt
?? new.txt

    의미: --porcelain은 사람이 아니라 스크립트가 파싱하기 좋은 고정된 형식으로 상태를 출력합니다. "커밋 전 최종 검증"을 자동화 스크립트에 넣을 때 이 형식을 씁니다.

2. log — 지나온 이력 들여다보기

log는 지금까지 쌓인 모든 커밋을 조회하는 명령입니다. "누가 언제 무엇을 왜 바꿨는지"를 되짚어볼 때 사용합니다.

log · 쉬움 10제

  1. $ git log
commit a1b2c3d... (HEAD -> main)
Author: kdt-student 
Date:   ...
    docs: 첫 메모 추가

    의미: 지금까지의 모든 커밋 이력을 확인하는 기본 명령입니다.

  2. $ git log --oneline
a1b2c3d docs: 첫 메모 추가
9f8e7d6 체크포인트

    의미: --oneline은 해시 앞자리+메시지만 간단히 보여줘 전체 흐름을 빠르게 훑을 때 씁니다.

  3. $ git log -3
(가장 최근 3개의 커밋만 출력)

    의미: 숫자를 붙이면 "최근 N개"만 제한해서 봅니다.

  4. $ git log --author="kdt-student"
(지정한 작성자의 커밋만 필터링되어 출력)

    의미: 여러 명이 협업할 때 "이 사람이 한 작업만" 골라볼 수 있습니다.

  5. $ git log --stat
commit a1b2c3d
    docs: 첫 메모 추가
 note.txt | 1 +
 1 file changed, 1 insertion(+)

    의미: 각 커밋마다 어떤 파일이 몇 줄 바뀌었는지 요약이 함께 표시됩니다.

  6. $ git log -p -1
(가장 최근 커밋의 실제 변경 내용(diff)까지 전부 표시)

    의미: -p(patch)는 커밋 메시지뿐 아니라 실제로 어떤 줄이 바뀌었는지 상세 내용을 보여줍니다.

  7. $ git log --since="2026-08-01"
(2026-08-01 이후에 만들어진 커밋만 출력)

    의미: 날짜 기준으로 이력을 필터링할 때 씁니다.

  8. $ git log -- note.txt
(note.txt 파일과 관련된 커밋들만 출력)

    의미: -- 파일명은 "이 파일과 관련된 커밋만" 필터링합니다.

  9. $ git show a1b2c3d
commit a1b2c3d
    docs: 첫 메모 추가
diff --git a/note.txt b/note.txt
+안녕하세요

    의미: 커밋 해시를 직접 지정해 "그 시점에 정확히 뭐가 바뀌었는지" 확인합니다.

  10. $ git log --graph --oneline
* a1b2c3d docs: 첫 메모 추가
* 9f8e7d6 체크포인트

    의미: 커밋들이 * 기호와 선으로 연결된 그래프 형태로 표시됩니다. 브랜치가 갈라지고 합쳐진 모양을 볼 때 진가를 발휘합니다.

log · 어려움 10제

  1. $ git log --pretty=format:"%h %ad %s" --date=short
a1b2c3d 2026-08-20 docs: 첫 메모 추가

    의미: --pretty=format으로 해시(%h), 날짜(%ad), 메시지(%s) 등 원하는 정보만 원하는 순서로 뽑을 수 있습니다.

  2. $ git log --grep="fix"
(커밋 메시지에 "fix"가 포함된 커밋만 출력)

    의미: 메시지 내용 기준으로 검색합니다. "버그 수정 이력만 모아보기" 같은 작업에 씁니다.

  3. $ git log -S"세번째"
(그 문자열이 추가되거나 삭제된 커밋만 찾아서 출력)

    의미: -S(pickaxe)는 "코드 내용 자체"에서 특정 문자열이 등장/사라진 커밋을 찾습니다. 언제 이 코드가 처음 생겼는지 추적할 때 강력합니다.

  4. $ git mv note.txt notes.txt && git commit -m "rename: note -> notes"
$ git log --follow -- notes.txt
(이름이 바뀌기 전 note.txt였을 때의 이력까지 포함해서 출력)

    의미: --follow는 파일 이름이 변경된 경우에도 그 이전 역사까지 추적합니다.

  5. $ git log main..feature-A
(main에는 없고 feature-A에만 있는 커밋 목록)

    의미: 두 브랜치 사이의 차이(feature-A가 main보다 앞서 가진 커밋)를 확인할 때 씁니다.

  6. $ git log --merges
(병합(merge) 커밋만 걸러서 출력)

    의미: 여러 브랜치가 언제 합쳐졌는지만 추적하고 싶을 때 씁니다.

  7. $ git log --no-merges
(병합 커밋을 제외한 "실제 작업 커밋"만 출력)

    의미: 머지 커밋으로 지저분해진 이력에서 진짜 변경 내용만 보고 싶을 때 씁니다.

  8. $ git log -L 1,3:notes.txt
(notes.txt 파일의 1~3번째 줄이 각 커밋에서 어떻게 바뀌어왔는지 이력 출력)

    의미: -L(line)은 파일 전체가 아니라 "특정 줄 범위"의 변경 역사만 추적하는 고급 기능입니다.

  9. $ git log --format="%H" -1 | xargs -I{} git show {}:notes.txt
(가장 최근 커밋 시점의 notes.txt 내용이 그대로 출력)

    의미: 여러 git 명령을 파이프로 연결해 "가장 최근 커밋의 특정 파일 내용"을 한 번에 뽑아내는 조합입니다.

  10. $ git shortlog -sn
     8  kdt-student

    의미: 작성자별 커밋 개수가 많은 순으로 요약 출력합니다. 팀 프로젝트에서 "누가 커밋을 몇 개 했는지" 기여도를 빠르게 파악할 때 씁니다.

3. restore / reset / revert — 되돌리기 3단계

Git의 되돌리기는 작업 폴더 → 스테이징 → 저장소(커밋) 3단계 중 "어디까지 되돌릴지"에 따라 쓰는 명령이 다릅니다. 이 구분이 Git에서 가장 헷갈리지만 가장 중요한 개념입니다.

되돌리기 · 쉬움 10제

  1. $ echo "실수로 수정" >> notes.txt
$ git restore notes.txt
(notes.txt가 마지막 커밋 상태로 돌아가며, 방금 한 수정 내용이 사라짐)

    의미: restore는 "아직 스테이징하지 않은 작업 폴더의 수정"을 취소합니다.

  2. $ echo "임시 수정" >> notes.txt
$ git add notes.txt
$ git restore --staged notes.txt
(스테이징만 취소되고, 작업 폴더의 수정 내용은 그대로 남음)

    의미: --staged는 "add한 것만 취소"하고 파일 내용 자체는 건드리지 않습니다.

  3. $ git status
(현재 상태에 따라 Untracked/Modified/Staged 등이 다르게 표시)

    의미: 되돌리기 전후로 항상 git status를 확인해 지금 어떤 상태인지 파악하는 습관이 중요합니다.

  4. $ git reset --soft HEAD~1
(가장 최근 커밋이 취소되지만, 그 변경 내용은 스테이징 상태로 그대로 남음)

    의미: --soft는 "커밋만 취소, 스테이징은 유지"합니다. 커밋 메시지를 다시 쓰고 싶을 때 씁니다.

  5. $ git reset --mixed HEAD~1
(커밋도 취소되고 스테이징도 풀리지만, 파일 내용은 작업 폴더에 그대로 남음)

    의미: 옵션 없이 그냥 git reset HEAD~1을 쓰면 이 --mixed가 기본값으로 적용됩니다.

  6. $ git reset --hard HEAD~1
(커밋과 스테이징, 파일 내용까지 전부 그 커밋 이전 상태로 완전히 되돌아감)

    의미: --hard는 가장 강력하고 위험한 되돌리기입니다. 수정 내용이 통째로 사라지므로 신중해야 합니다.

  7. $ git revert HEAD
[main 4d5e6f7] Revert "docs: 첫 메모 추가"

    의미: revert는 되돌리되 이력을 지우지 않고 "취소했다는 기록"을 새로 남기는, 공유된 브랜치에서 안전한 방법입니다.

  8. $ git checkout -- notes.txt
(restore와 동일하게 작업 폴더의 수정 내용이 취소됨)

    의미: 최신 git은 restore를 권장하지만, 오래된 예제나 문서에서는 이 checkout -- 방식을 아직도 자주 봅니다.

  9. $ git reset HEAD notes.txt
(notes.txt만 스테이징에서 빠지고 나머지 파일은 그대로 스테이징 유지)

    의미: restore --staged의 예전 표현입니다. 파일명을 지정하면 그 파일만 대상이 됩니다.

  10. $ git log --oneline
(reset/revert 이후 커밋 목록이 어떻게 바뀌었는지 확인)

    의미: 되돌리기 작업 후에는 항상 log로 결과를 확인하는 것이 안전합니다.

되돌리기 · 어려움 10제

  1. $ git reset --hard 9f8e7d6
(지정한 커밋 시점 상태로 모든 것이 되돌아감)

    의미: HEAD~1처럼 상대적 위치가 아니라, 특정 커밋 해시를 직접 지정해 원하는 시점으로 정확히 이동합니다.

  2. $ git reflog
a1b2c3d HEAD@{0}: reset: moving to 9f8e7d6
4d5e6f7 HEAD@{1}: revert: Revert "docs: 첫 메모 추가"

    의미: reset이나 checkout 등으로 "안 보이게 된" 커밋까지 포함한 모든 HEAD 이동 기록입니다. reset --hard로 실수로 커밋을 날려도 복구할 수 있는 최후의 안전망입니다.

  3. $ git reset --hard HEAD@{2}
(reflog에서 확인한 2단계 이전 상태로 정확히 되돌아감)

    의미: reflog에서 찾은 시점(HEAD@{번호})으로 직접 이동해 "삭제된 것처럼 보였던" 커밋을 복구합니다.

  4. $ git revert --no-commit HEAD~2..HEAD
(최근 2개 커밋을 취소하는 변경사항이 스테이징에만 반영되고 커밋은 아직 안 됨)

    의미: --no-commit은 여러 revert를 한 번에 모아서 커밋 하나로 정리하고 싶을 때 씁니다.

  5. $ git checkout 9f8e7d6 -- notes.txt
(저장소 전체가 아니라 notes.txt 파일 하나만 그 커밋 시점 내용으로 교체됨)

    의미: 전체를 되돌리지 않고 "이 파일만" 예전 버전으로 가져오고 싶을 때 씁니다.

  6. $ git revert -m 1 <머지커밋해시>
(머지로 합쳐졌던 변경사항 전체가 취소되는 새 커밋 생성)

    의미: 일반 revert는 머지 커밋에 그냥 쓸 수 없고, -m 1로 "어느 부모 기준으로 되돌릴지" 지정해야 합니다.

  7. $ git reset --keep HEAD~1
(커밋은 취소되지만, 아직 커밋되지 않은 다른 작업 중인 변경사항은 안전하게 보존됨)

    의미: --mixed/--hard와 달리, 이미 작업 중이던(스테이징 안 된) 변경을 실수로 날리지 않도록 보호하며 되돌립니다.

  8. $ git diff HEAD~1 HEAD
(되돌리려는 커밋이 실제로 어떤 내용을 바꿨는지 diff로 미리 확인)

    의미: reset이나 revert를 실행하기 전에, 무엇이 취소될지 diff로 먼저 확인하는 것이 안전한 습관입니다.

  9. $ echo "아직 커밋 안 한 소중한 작업" >> notes.txt
$ git stash
$ git reset --hard HEAD~1
$ git stash pop
(임시 저장해둔 변경사항은 reset의 영향을 받지 않고 그대로 복원됨)

    의미: reset --hard 전에 아직 커밋하지 않은 소중한 변경사항이 있다면 stash로 잠시 빼두면 안전합니다.

  10. $ git reset --hard origin/main
(로컬의 모든 변경사항을 버리고 원격 저장소의 main 브랜치 상태와 완전히 동일하게 맞춤)

    의미: 로컬에서 뭔가 심하게 꼬였을 때 "원격 기준으로 완전히 리셋"하는 최후의 수단입니다(로컬 변경사항은 전부 사라지므로 매우 신중해야 합니다). 원격 저장소는 D7에서 본격적으로 다룹니다.

4. branch / merge — 갈라지고 합치기

branch는 "원본을 건드리지 않고 안전하게 실험할 별도의 작업 공간"을 만드는 것이고, merge는 그 실험 결과를 다시 원래 흐름에 합치는 것입니다.

branch/merge · 쉬움 10제

  1. $ git branch
* main

    의미: 지금 저장소에 어떤 브랜치들이 있고, 내가 지금 어디 있는지(*) 확인합니다.

  2. $ git branch feature-A
(출력 없음 — feature-A 브랜치가 생성되지만 아직 이동은 안 됨)

    의미: branch 뒤에 이름만 쓰면 "만들기만" 하고 브랜치 전환은 하지 않습니다.

  3. $ git switch feature-A
Switched to branch 'feature-A'

    의미: switch로 그 브랜치로 이동(전환)합니다.

  4. $ git switch -c feature-B
Switched to a new branch 'feature-B'

    의미: -c(create)를 붙이면 branch+switch를 한 번에 처리합니다. 실무에서 가장 많이 쓰는 형태입니다.

  5. $ git switch main
Switched to branch 'main'

    의미: 언제든 이름만 지정하면 그 브랜치로 돌아갈 수 있습니다.

  6. $ echo "feature-A 작업" >> notes.txt   # (feature-A 브랜치에서 커밋해둔 상태 가정)
$ git switch main
$ git merge feature-A
Merge made by the 'ort' strategy.
 notes.txt | 1 +

    의미: 지금 있는 브랜치(main)에 다른 브랜치(feature-A)의 내용을 합칩니다.

  7. $ git branch -d feature-A
Deleted branch feature-A (was 1a2b3c4).

    의미: -d는 이미 main에 합쳐진(안전한) 브랜치만 삭제를 허용합니다.

  8. $ git branch -a
* main
  feature-B
  remotes/origin/main

    의미: -a(all)로 원격 브랜치까지 포함해서 볼 수 있습니다(원격은 D7에서 본격적으로 다룹니다).

  9. $ git branch -m feature-B feature-B-renamed
(feature-B 브랜치가 feature-B-renamed로 이름이 바뀜)

    의미: -m(move/rename)으로 브랜치 이름을 잘못 지었을 때 고칠 수 있습니다.

  10. $ git log --oneline --graph --all
*   7a8b9c0 Merge branch 'feature-A'
|\
| * 1a2b3c4 feature-A 작업
|/
* a1b2c3d docs: 첫 메모 추가

    의미: merge 전후 커밋 구조가 어떻게 달라졌는지 눈으로 확인하는 가장 좋은 방법입니다.

branch/merge · 어려움 10제

  1. $ git merge feature-C
Auto-merging notes.txt
CONFLICT (content): Merge conflict in notes.txt
Automatic merge failed; fix conflicts and then commit the result.

    의미: 두 브랜치가 같은 줄을 다르게 고쳤을 때 git이 자동으로 합치지 못하고 사람의 판단을 요청합니다.

  2. $ cat notes.txt
<<<<<<< HEAD
main에서 고친 내용
=======
feature-C에서 고친 내용
>>>>>>> feature-C
$ nano notes.txt   # 마커를 지우고 원하는 내용으로 직접 정리
$ git add notes.txt
$ git commit
(별도 -m 없이도 "Merge branch 'feature-C'" 형태의 기본 메시지로 커밋 완료)

    의미: 충돌은 "둘 중 하나를 고르거나 둘을 합쳐서" 사람이 직접 정리해야 하며, add로 "해결 완료"를 git에 알려줍니다.

  3. $ git merge --abort
(merge를 시도하기 이전 상태로 완전히 되돌아감)

    의미: 충돌 해결이 너무 복잡하거나 실수로 시작한 merge라면, --abort로 안전하게 중단하고 처음부터 다시 생각할 수 있습니다.

  4. $ git merge --no-ff feature-D
Merge made by the 'ort' strategy.

    의미: --no-ff는 단순히 앞으로 이동만 해도 되는 상황에서도 굳이 별도의 병합 커밋을 하나 만들어, "이 기능이 별도 브랜치에서 개발되었다"는 흔적을 이력에 남깁니다(팀 프로젝트에서 자주 쓰는 정책).

  5. $ git branch --merged
* main
  feature-D

    의미: 이미 현재 브랜치에 완전히 합쳐진 브랜치 목록만 표시합니다. "삭제해도 안전한 브랜치가 어떤 것들인지" 확인할 때 씁니다.

  6. $ git branch --no-merged
  feature-E

    의미: 반대로 아직 합쳐지지 않은(작업 중인) 브랜치 목록만 표시합니다. "아직 살려둬야 할 브랜치"를 확인할 때 씁니다.

  7. $ git diff main feature-E
(두 브랜치 사이의 모든 차이(diff)가 출력)

    의미: 병합하기 전에 "합치면 정확히 무엇이 바뀌는지" 미리 확인하는 안전한 습관입니다.

  8. $ git branch -D feature-F
Deleted branch feature-F (was 5e6f7a8).

    의미: 소문자 -d는 안전장치가 있어 미병합 브랜치를 거부하지만, 대문자 -D는 그 안전장치를 무시하고 강제로 지웁니다.

  9. $ git switch -c hotfix main~3
Switched to a new branch 'hotfix'

    의미: 브랜치는 항상 최신에서 시작할 필요가 없습니다. main~3처럼 과거 특정 시점을 기준으로 새 작업을 시작할 수도 있습니다.

  10. $ git switch feature-G
$ git rebase main
Successfully rebased and updated refs/heads/feature-G.

    의미: merge와 달리 rebase는 이력을 "일직선으로 재작성"합니다. 다만 이미 공유된 브랜치에는 절대 쓰지 않아야 한다는 원칙을 꼭 기억해야 합니다(D6 본문의 실무 확장 미션에서 자세히 다룹니다).

5. tag · .gitignore · stash — 핵심만 10개

변형이 많지 않은 명령들이라 쉬움/어려움을 나누지 않고, 꼭 필요한 10개를 표로 정리했습니다.

번호명령예상 결과의미
1git tag v1.0현재 커밋에 v1.0이라는 이름표가 붙음릴리스나 제출 시점에 이름을 붙여 나중에 쉽게 찾도록 표시합니다
2git tagv1.0, v1.1 등 지금까지 만든 태그 목록 출력태그 전체를 확인합니다
3git tag -a v1.0 -m "1차 제출"메시지가 포함된 상세 태그(annotated tag) 생성누가 언제 왜 이 지점을 표시했는지 기록을 남길 때 씁니다
4git checkout v1.0그 태그가 가리키는 커밋 시점으로 파일들이 이동(detached HEAD 상태)과거 제출 시점의 코드를 그대로 살펴볼 때 씁니다
5git tag -d v1.0v1.0 태그가 삭제됨잘못 붙인 태그를 지울 때 씁니다
6echo "*.jpg" >> .gitignore.gitignore 파일에 규칙이 한 줄 추가됨특정 패턴의 파일을 git이 앞으로 무시하도록 지정합니다
7git check-ignore -v sample.jpg.gitignore:1:*.jpg sample.jpg 처럼 어느 규칙 때문에 무시되는지 출력왜 이 파일이 안 보이는지 원인을 진단할 때 씁니다
8git stash작업 중이던 변경사항이 임시 저장되고 작업 폴더가 깨끗해짐커밋 전 급히 다른 작업(브랜치 전환 등)을 해야 할 때 씁니다
9git stash liststash@{0}: WIP on main: ... 저장된 stash 목록 출력지금까지 임시 저장해둔 것이 몇 개인지 확인합니다
10git stash pop가장 최근 stash가 다시 적용되고 목록에서 제거됨임시로 치워뒀던 작업을 다시 이어서 할 때 씁니다

한눈에 정리

명령어한 줄 정의가장 많이 쓰는 옵션실무에서 이럴 때 쓴다
add / commit변경사항을 준비하고 저장 시점을 남긴다-m -am -A -p --amend의미 단위로 작업을 나눠 커밋할 때
log지나온 커밋 이력을 조회한다--oneline --graph --author --grep누가 무엇을 언제 왜 바꿨는지 추적할 때
restore/reset/revert변경사항이나 커밋을 되돌린다--staged --soft --hard revert실수한 수정 취소, 안전한 공개 이력 되돌리기
branch / merge작업을 나누고 다시 합친다switch -c merge --no-ff -d/-D기능별로 독립 개발 후 팀 브랜치에 통합할 때
tag / gitignore / stash특정 지점을 표시하고, 파일을 무시하고, 작업을 잠시 치운다tag -a check-ignore stash pop제출 시점 표시, 민감 파일 제외, 급한 브랜치 전환
