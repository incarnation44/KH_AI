리눅스 시스템 구조와 운영체제 개론 — 왜, 그리고 어떻게 리눅스로 개발하는가

커널 · 시스템 콜 · 프로세스 모델 · 타 OS 비교 — CLI 명령을 "그냥 외우는 것"에서 "왜 그렇게 동작하는지 아는 것"으로

D1 이수이 문서 (보충)D2로 이어짐

오늘의 한 문장: "cat file.txt 한 줄 뒤에서 커널이 실제로 무슨 일을 하는지 눈으로 확인한다."

왜 이 문서를 따로 공부하는가

D1에서 여러분은 ls, cd, mkdir 같은 명령어로 리눅스를 "사용"하는 법을 배웠습니다. 이 문서는 그 명령어 뒤편, 즉 "이 명령을 치면 컴퓨터 안에서 실제로 무슨 일이 일어나는가"를 다룹니다.

비전공자에게 이 내용이 왜 필요한지 먼저 답하고 시작하겠습니다.

이 과정에서 마주칠 순간이 문서가 주는 답
AWS GPU 서버, Jetson, Raspberry Pi가 모두 "리눅스"인 이유커널과 배포판의 관계 — 하드웨어가 달라도 리눅스 커널의 인터페이스는 동일합니다
Windows 11 노트북인데 왜 WSL로 Ubuntu를 또 까는가OS 커널이 다르면 프로그램이 실행되는 방식(시스템 콜)이 다르기 때문 — CUDA·PyTorch 생태계는 리눅스 커널 위에서 표준화되어 있습니다
딥러닝 학습이 "메모리 부족(OOM)"으로 죽는 이유OS가 프로세스에 메모리를 어떻게 배분·회수하는지 알면 원인이 보입니다 (교과 4·5 실습에서 실제로 겪게 됩니다)
Docker 컨테이너가 "가상머신보다 가볍다"는 말의 의미컨테이너는 커널을 공유하고, 가상머신은 커널까지 통째로 새로 띄운다는 구조 차이입니다
면접에서 "리눅스와 윈도우의 차이가 뭔가요?" 질문"커널 구조·오픈소스 여부·파일시스템·용도" 4가지 축으로 답변할 수 있습니다

즉 이 문서의 목적은 암기가 아니라 "그림이 그려지는 것"입니다. 명령어 하나를 배울 때마다 "커널에게 무엇을 요청하는 중이구나"라는 감각이 생기면 성공입니다.

PART 1. 이론

1교시 · 운영체제란 무엇인가

1.1 컴퓨터에는 왜 OS가 필요한가

컴퓨터 하드웨어(CPU, RAM, 디스크, 네트워크 카드, GPU)는 그 자체로는 "0과 1을 계산하는 회로 덩어리"일 뿐입니다. 여러분이 만드는 파이썬 프로그램, 크롬 브라우저, 카카오톡이 이 회로를 직접 두드린다면 어떻게 될까요?

  • 두 프로그램이 동시에 같은 메모리 주소를 쓰려고 하면 → 충돌
  • 한 프로그램이 디스크 전체를 지워버리면 → 다른 프로그램의 데이터도 함께 증발
  • 수십 개 프로그램이 "내가 먼저 CPU 쓸래"라고 각자 우기면 → 아무것도 안 됨

운영체제(OS, Operating System)는 이 문제를 해결하기 위해 하드웨어와 응용 프로그램 사이에 서서 자원을 중재하고 관리하는 소프트웨어입니다. 딱 네 가지 자원만 기억하면 됩니다.

관리 대상OS가 하는 일여러분이 곧 만날 예
CPU (연산)어떤 프로그램에 언제 CPU 시간을 줄지 결정(스케줄링)딥러닝 학습 중 top으로 CPU 점유율 확인
메모리 (RAM)프로그램마다 독립된 메모리 공간을 배분, 부족하면 회수/거부배치 크기를 올렸다가 OOM Killed 를 보게 되는 순간
저장장치 (파일)디스크의 물리적 위치를 숨기고 "파일과 디렉토리"라는 추상화 제공D1에서 배운 /home/kdt/dataset/... 경로 체계
입출력 장치키보드, 네트워크, GPU 등 장치마다 다른 방식을 표준 인터페이스로 통일USB 카메라를 꽂아도 어떤 브랜드든 같은 방식으로 접근 가능

한 줄 정의: OS는 "하드웨어를 프로그램이 쓰기 쉽고 안전하게 나눠 쓸 수 있도록 포장해 주는 계층"입니다.

1.2 "리눅스"는 그 중에서도 "커널"이다

흔히 "리눅스"라고 부르는 것은 정확히는 리눅스 커널(Kernel)을 가리킵니다. 커널은 OS의 핵심부로, 위에서 말한 CPU·메모리·파일·장치 관리를 실제로 수행하는 프로그램입니다. 우리가 평소 "리눅스를 쓴다"고 할 때는 이 커널 위에 셸(bash), 각종 유틸리티(ls, grep...), 패키지 관리자를 얹어 배포하는 배포판(Distribution), 예를 들어 Ubuntu·Debian·CentOS를 사용하는 것입니다.

[ 여러분이 타이핑 ]  →  [ 셸(bash) ]  →  [ 시스템 콜 ]  →  [ 리눅스 커널 ]  →  [ 하드웨어 ]
      $ ls                해석 · 실행         open/read           스케줄링 · 메모리 관리    CPU/디스크

Ubuntu, Raspberry Pi OS, Jetson의 L4T(Linux for Tegra)는 모두 같은 리눅스 커널 계열을 씁니다. 그래서 교과 13 Raspberry Pi와 교과 14 Jetson에서 여러분이 배운 리눅스 명령어가 그대로 통하는 것입니다 — 배포판 포장지는 달라도 커널이 제공하는 약속(시스템 콜)이 같기 때문입니다.

2교시 · 커널·사용자 공간과 시스템 콜

2.1 커널 공간과 사용자 공간

안전을 위해 CPU는 실행 권한을 두 단계로 나눕니다.

구분권한실행되는 것
커널 모드 (Kernel Mode)하드웨어에 직접 접근 가능한 최고 권한커널 코드 자체 — 메모리 관리자, 디스크 드라이버 등
사용자 모드 (User Mode)제한된 권한. 하드웨어에 직접 접근 불가여러분이 만든 파이썬 스크립트, bash, VS Code 등 모든 일반 프로그램

일반 프로그램(사용자 모드)이 파일을 읽거나, 네트워크로 데이터를 보내거나, 새 프로세스를 만들려면 — 즉 하드웨어 자원이 필요할 때마다 — 직접 손댈 수 없으므로 커널에게 "이 작업을 대신 해 달라"고 정중히 요청해야 합니다. 이 요청 메커니즘이 바로 시스템 콜(System Call)입니다.

2.2 시스템 콜이란 정확히 무엇인가

시스템 콜: 사용자 모드 프로그램이 커널 모드의 기능을 사용하기 위해 호출하는, OS가 제공하는 표준화된 창구(인터페이스)

예를 들어 파이썬에서 print("hello")를 실행하면, 내부적으로 다음과 같은 순서를 거칩니다.

1. 파이썬 인터프리터(사용자 모드)가 "화면에 문자열을 출력하고 싶다"고 판단
2. C 표준 라이브러리의 printf() 같은 함수를 호출
3. printf() 내부에서 write() 시스템 콜을 호출 → 사용자 모드에서 커널 모드로 전환
4. 커널이 실제로 화면(표준출력) 장치에 데이터를 씀
5. 커널 모드 → 사용자 모드로 복귀, 프로그램 실행 계속

즉 화면에 글자 하나 찍는 것조차 커널의 허락과 대행 없이는 불가능합니다. 실습 A-3에서 이 과정을 strace로 직접 눈으로 확인합니다.

2.3 대표 시스템 콜 훑어보기

전부 외울 필요는 없습니다. 아래 표는 "앞으로 배울 명령어·API가 결국 이 중 하나를 부르는구나"를 연결하는 지도입니다.

분류대표 시스템 콜일상에서 만나는 모습
파일open, read, write, closeD2에서 배운 cat, cp, 파이썬의 open()
프로세스fork, execve, exit, waitD4에서 배울 ./script.sh 실행, 백그라운드(&) 작업
메모리mmap, brk파이썬이 대용량 이미지 배열을 메모리에 올릴 때

2.4 시스템 콜과 "라이브러리 함수"는 다르다 ★자주 헷갈리는 지점

시스템 콜라이브러리 함수
제공 주체커널glibc, 파이썬 표준 라이브러리 등
예write()printf(), 파이썬 print()

실무 힌트: 파이썬으로 대용량 로그 파일을 한 줄씩 file.write()할 때마다 매번 디스크에 쓰지 않고 버퍼에 모았다가 한 번에 쓰는 이유가 여기 있습니다 — 시스템 콜 호출 횟수 자체가 성능에 영향을 주기 때문입니다.

3교시 · 리눅스 아키텍처 전체 그림

3.1 계층 구조

┌─────────────────────────────────────────────┐
│  응용 프로그램        python, git, vim, chrome  │  ← 사용자 모드
├─────────────────────────────────────────────┤
│  셸 & 유틸리티        bash, ls, grep, awk       │  ← 사용자 모드
├─────────────────────────────────────────────┤
│  ─ ─ ─ ─ ─ ─  시스템 콜 인터페이스  ─ ─ ─ ─ ─ ─  │  ← 경계선 (User ↔ Kernel)
├─────────────────────────────────────────────┤
│  커널                                          │  ← 커널 모드
│   ┌───────────┬───────────┬────────────┐     │
│   │ 프로세스   │ 메모리     │ 파일시스템/  │     │
│   │ 스케줄러   │ 관리자     │ 네트워크    │     │
│   └───────────┴───────────┴────────────┘     │
│              디바이스 드라이버                  │
├─────────────────────────────────────────────┤
│  하드웨어           CPU · RAM · 디스크 · GPU 등  │
└─────────────────────────────────────────────┘

D1~D4에서 배우는 모든 명령어는 이 그림에서 "셸 & 유틸리티" 층에 있으며, 실행되면 반드시 점선(시스템 콜 경계)을 넘어 커널에 일을 시킵니다.

3.2 부팅부터 프롬프트까지 한 줄 요약

전원 ON → 부트로더(GRUB) → 커널 적재 → init/systemd 시작
→ 각종 서비스(네트워크, SSH 등) 기동 → 로그인 → 셸(bash) 실행 → 프롬프트 $ 표시

D1에서 만난 systemctl status ssh 같은 명령이 바로 위 과정 중 "서비스 기동" 부분을 들여다보는 도구입니다.

3.3 프로세스 — 예고편 (D4에서 본격적으로 다룸)

커널은 실행 중인 프로그램 하나하나를 프로세스(Process)라는 단위로 관리합니다. 새 프로그램은 항상 다음 두 시스템 콜의 조합으로 태어납니다.

  • fork() — 현재 프로세스(예: bash)를 복제해 자식 프로세스를 만든다
  • execve() — 그 자식 프로세스의 내용을 새 프로그램(예: python)으로 갈아끼운다

즉 터미널에서 python train.py를 치면, bash는 자기 자신을 fork()로 복제한 뒤 그 복제본을 execve()로 python 프로그램으로 바꿔치기합니다. 이 개념은 D4 실습 A-4와 D4 프로세스 수업에서 ps --forest로 직접 확인합니다.

4.2 왜 AI·데이터 개발자는 결국 리눅스를 쓰게 되는가

이유구체적 근거
클라우드 GPU 서버가 사실상 전부 리눅스AWS g5.xlarge(교과 5·11에서 사용)를 포함, 주요 클라우드 GPU 인스턴스 이미지는 Ubuntu 계열이 기본값
CUDA·딥러닝 프레임워크의 1급 지원 플랫폼PyTorch·TensorFlow의 GPU 최적화 빌드는 리눅스에서 가장 먼저, 가장 안정적으로 제공됩니다
Docker·Kubernetes가 리눅스 커널 기능 위에서 동작컨테이너는 리눅스 커널의 namespace·cgroup 기능을 이용 — Windows/macOS에서 Docker를 쓰려면 내부적으로 리눅스 가상머신을 하나 띄웁니다
임베디드 보드의 표준교과 13 Raspberry Pi, 교과 14 Jetson Orin Nano 모두 리눅스 기반 OS로 부팅됩니다
오픈소스 생태계대부분의 AI 논문 공식 구현체가 리눅스 환경 기준으로 배포·검증됩니다

4.3 리눅스의 장단점 — 균형 있게 보기

장점단점
무료 · 오픈소스, 소스 열람·수정 자유초심자에게 GUI 편의성이 Windows/macOS 대비 낮음(CLI 학습 필요 — 여러분이 지금 하는 중)
서버 운영에 필요한 자원만 가볍게 구성 가능상용 소프트웨어(일부 CAD, 특정 그래픽 툴 등) 지원이 제한적
보안 패치·커널 업데이트가 빠르고 투명함배포판·버전마다 미묘한 차이로 "내 컴퓨터에선 되는데" 문제 발생 가능
자동화·원격 관리(SSH, cron)에 최적화하드웨어 드라이버(특히 최신 노트북 지문인식 등) 지원이 늦을 수 있음
동일 커널 인터페이스로 서버~임베디드까지 일관된 학습 이전 가능배포판별 패키지 관리 방식이 달라 학습 곡선 존재

4.4 이 과정에서 쓰는 환경 — WSL2도 결국 "리눅스 커널"이다

여러분의 실습 PC는 Windows 11이지만, WSL2(Windows Subsystem for Linux 2)는 진짜 리눅스 커널을 경량 가상머신으로 부팅하는 방식입니다. 즉 지금 여러분이 터미널에서 실행하는 모든 명령은 "리눅스 커널 위에서" 그대로 처리되며, 이 문서에서 배운 시스템 콜·프로세스 개념이 100% 동일하게 적용됩니다. 실습 A-5에서 이를 직접 확인합니다.

PART 2. 실습

실습 A-1 · 내 리눅스의 신원 확인하기

목적: 지금 내가 어떤 커널·배포판 위에서 작업하고 있는지 "증명서"를 확인합니다. 트러블슈팅 시 가장 먼저 확인하는 정보이기도 합니다.

# M1. 커널 버전과 아키텍처
uname -a
# 출력 예: Linux DESKTOP-XXXX 5.15.153.1-microsoft-standard-WSL2 ... x86_64 GNU/Linux
#          └ WSL2 커널임이 여기서 드러납니다

# M2. 배포판 이름 · 버전
cat /etc/os-release

# M3. CPU 코어 수, 아키텍처 확인 (AI 학습 성능 추정의 출발점)
nproc
lscpu | head -15

설명: uname -a의 출력 안에 microsoft-standard-WSL2라는 문자열이 보인다면, 이것이 곧 "리눅스 커널이되, Microsoft가 WSL2용으로 빌드한 버전"이라는 증거입니다. Jetson에서 같은 명령을 치면 tegra라는 문자열이, AWS 서버에서 치면 aws 관련 문자열이 보일 수 있습니다 — 배포처는 다르지만 명령어 사용법은 동일하다는 점이 핵심입니다.

✅ 체크포인트 A-1

  • [ ] 내 WSL2의 커널 버전을 확인했다
  • [ ] /etc/os-release에서 Ubuntu 버전을 확인했다

실습 A-2 · /proc 파일시스템 탐험

목적: 커널은 자신이 관리하는 정보(CPU, 메모리, 실행 중인 프로세스 등)를 가짜 파일의 형태로 사용자에게 공개합니다. 이것이 /proc입니다. "커널 상태를 파일 읽듯이 들여다본다"는 리눅스 철학("모든 것은 파일이다")을 체감하는 실습입니다.

# M4. CPU 정보 — 딥러닝 서버 스펙 확인 시 실무에서 그대로 사용
cat /proc/cpuinfo | grep "model name" | head -1
cat /proc/cpuinfo | grep -c processor   # 논리 코어 수

# M5. 메모리 정보 — OOM(메모리 부족) 트러블슈팅의 시작점
cat /proc/meminfo | head -5

# M6. 내 셸 프로세스 자신의 정보 들여다보기
echo "내 bash의 PID: $$"
cat /proc/$$/status | head -10
ls /proc/$$/

# M7. 현재 커널이 지원하는 시스템 콜 개수 어림 확인(참고용)
ls /proc/sys/kernel | wc -l

설명: /proc/$$/status는 지금 이 명령을 실행 중인 bash 프로세스 "자기 자신"의 상태(부모 PID, 메모리 사용량, 상태 등)를 커널이 실시간으로 만들어 보여주는 파일입니다. 실제로 디스크에 저장된 파일이 아니라, 읽는 순간 커널이 즉석에서 생성합니다 — ls -l로 보면 파일 크기가 0바이트로 나오는 것이 그 증거입니다.

✅ 체크포인트 A-2

  • [ ] 내 PC의 CPU 모델명과 코어 수를 확인했다
  • [ ] /proc/$$/status로 현재 셸 프로세스 정보를 확인했다
  • [ ] "/proc은 실제 파일이 아니라 커널이 즉석 생성한다"는 문장을 본인 말로 설명할 수 있다

실습 A-3 · strace로 시스템 콜 직접 보기 ★핵심

목적: 2교시에서 배운 "명령 하나 = 시스템 콜 여러 개"를 눈으로 직접 확인합니다. 이 실습이 이 문서 전체의 핵심입니다.

# 설치 확인 (WSL Ubuntu에 기본 포함되지 않을 수 있음)
sudo apt update && sudo apt install -y strace

mkdir -p ~/kdt-linux/os-lab && cd ~/kdt-linux/os-lab
echo "hello kdt" > sample.txt

3.3.1 cat 한 줄 뒤의 시스템 콜

# M8. cat 실행 시 호출되는 시스템 콜 전체 추적
strace cat sample.txt

설명: 출력이 매우 길게 나오지만, 핵심은 openat(...) → read(...) → write(...) → close(...) 네 줄입니다. 여러분이 "파일을 화면에 출력한다"고 표현한 한 문장이, 커널 입장에서는 "파일을 열고, 읽고, 화면(표준출력)에 쓰고, 닫는" 4단계 요청이었음을 확인합니다.

# M9. 관심 있는 시스템 콜만 필터링해서 보기
strace -e trace=open,openat,read,write,close cat sample.txt

# M10. 몇 번 호출되었는지 통계로 요약(-c)
strace -c cat sample.txt

3.3.2 파이썬 스크립트 추적하기

cat > read_test.py << 'EOF'
with open("sample.txt") as f:
    data = f.read()
print(data)
EOF

# M11. 파이썬이 파일을 열 때도 결국 open/read/write를 호출하는지 확인
strace -e trace=openat,read,write,close python3 read_test.py

설명: 파이썬의 open(), .read(), print()가 각각 커널의 openat, read, write 시스템 콜로 이어지는 것을 확인할 수 있습니다. "파이썬 문법"과 "OS 시스템 콜"이 이 지점에서 만난다는 것이 이 실습의 결론입니다.

3.3.3 네트워크 시스템 콜 예고편

# M12. ping 한 번에도 socket 시스템 콜이 등장합니다 (Ctrl+C로 중단)
strace -e trace=socket,connect ping -c 2 8.8.8.8

✅ 체크포인트 A-3

  • [ ] strace cat 출력에서 open→read→write→close 순서를 찾았다
  • [ ] strace -c로 시스템 콜별 호출 횟수 요약을 확인했다
  • [ ] 파이썬 open()이 openat 시스템 콜로 이어짐을 확인했다

실습 a-4 · 프로세스 트리로 보는 fork · exec

목적: 3.3절 이론에서 배운 "bash가 자신을 fork()한 뒤 execve()로 새 프로그램으로 바꾼다"는 과정을 프로세스 트리로 확인합니다.

# M13. 현재 프로세스 트리 확인
pstree -p $$

# M14. 새 프로세스를 하나 띄우고, 그 부모가 지금 이 bash임을 확인
sleep 60 &
BGPID=$!
ps -ef --forest | grep -A1 -B1 sleep

# M15. 새로 뜬 프로세스의 부모 PID(PPID) 확인
ps -o pid,ppid,cmd -p $BGPID
echo "내 셸의 PID: $$"

kill $BGPID   # 정리

설명: sleep 60 &을 실행하면 bash는 자기 자신을 fork()로 복제(자식 bash 생성)한 뒤, 그 자식을 execve()로 sleep 프로그램으로 바꿔칩니다. ps -o pid,ppid로 확인한 PPID(부모 PID)가 여러분의 $$(현재 셸 PID)와 일치하는 것이 그 증거입니다. 이 fork+exec 패턴은 D4에서 여러분이 만들 모든 셸 스크립트, 그리고 교과 14의 파이썬 서브프로세스 호출에서도 동일하게 반복됩니다.

✅ 체크포인트 A-4

  • [ ] 백그라운드 프로세스의 PPID가 내 셸의 PID와 같음을 확인했다
  • [ ] "fork로 복제 후 exec로 바꿔친다"를 본인 말로 설명할 수 있다

실습 A-5 · WSL2 아키텍처 직접 확인하기

목적: 4.4절에서 배운 "WSL2는 진짜 리눅스 커널을 가상머신으로 띄운다"는 사실을, Windows 파일시스템과의 경계를 통해 직접 체감합니다.

# M16. WSL2 전용 커널 버전 문자열 재확인
cat /proc/version

# M17. Windows 드라이브가 리눅스 파일시스템에 마운트되는 지점
ls /mnt/c/Users/ 2>/dev/null | head -5

# M18. 반대로 리눅스 파일시스템은 Windows 탐색기에서 접근 어려움 확인(개념 설명용)
pwd
echo "이 경로는 Windows 탐색기 주소창에 \\\\wsl\$\\Ubuntu 형태로만 접근 가능합니다"

# M19. WSL의 init 프로세스 확인
ps -p 1 -o pid,comm

설명: /mnt/c/... 는 Windows의 C 드라이브를 리눅스 파일시스템 트리 안에 "마운트"한 지점입니다. 이는 4.1절 표에서 본 "리눅스는 드라이브 문자 없이 단일 트리를 쓴다"는 특징이 WSL2 환경에서 Windows와 어떻게 공존하는지 보여주는 실제 사례입니다. 데이터 보안 정책(㈜비솔 제공 데이터의 폐쇄망 원칙)을 다룰 D7에서, 이 마운트 경계가 왜 중요한지 다시 연결됩니다.

✅ 체크포인트 A-5

  • [ ] /proc/version에서 WSL2 커널 문자열을 확인했다
  • [ ] /mnt/c가 Windows 드라이브의 마운트 지점임을 확인했다

실습 A-6 · 종합 챌린지 — 시스템콜 집계 리포트

미션: 앞서 만든 read_test.py를 strace -c로 추적하고, 호출 횟수가 가장 많은 시스템 콜 상위 3개를 syscall_report.txt에 저장하시오.

cd ~/kdt-linux/os-lab
{
  echo "===== 시스템콜 집계 리포트 ====="
  echo "대상: read_test.py"
  echo "생성일시: $(date '+%Y-%m-%d %H:%M')"
  echo ""
  strace -c python3 read_test.py 2>&1 | tail -n +3 | head -n -2
} | tee syscall_report.txt

  • [ ] syscall_report.txt가 생성되었다
  • [ ] 상위 3개 시스템 콜이 무엇이고, 왜 그 순서인지 한 문장으로 설명할 수 있다

마무리 

cd ~/kdt-linux
cat > OS_INTRO.md << 'EOF'
# D1+ — OS 개론 · 리눅스 시스템 구조와 시스템콜
## 핵심 개념
- OS = 하드웨어(CPU·메모리·디스크·장치)를 프로그램에 안전하게 나눠주는 계층
- 리눅스 = 커널. Ubuntu/Raspberry Pi OS/L4T는 모두 같은 커널 계열 위의 배포판
- 커널 모드 vs 사용자 모드, 그 경계를 넘는 창구 = 시스템 콜
- 대표 시스템 콜: open/read/write/close, fork/execve, mmap, socket
- 새 프로세스는 fork() 복제 + execve() 교체로 태어난다
- WSL2 = 진짜 리눅스 커널을 가상머신으로 구동
## 실무 도구
- uname -a, /etc/os-release : 환경 신원 확인
- /proc : 커널 상태를 파일처럼 열람
- strace : 시스템 콜 실시간 관찰(트러블슈팅 필수 도구)
- pstree, ps --forest : 프로세스 부모-자식 관계 확인
EOF

과제

  1. strace -c ls -la / 결과에서 호출 횟수 1위 시스템 콜과 그 이유를 추측해 쓰시오.
  2. "라이브러리 함수"와 "시스템 콜"의 차이를 본인의 언어로 3줄 이내로 설명하시오.
  3. Jetson(교과 14)이나 Raspberry Pi(교과 13)에서도 오늘 배운 uname -a, strace가 그대로 동작할 것으로 예상하는 이유를 쓰시오.
  4. Windows에서 직접 파이썬을 돌리는 것과, WSL2 Ubuntu 안에서 돌리는 것의 차이를 이 문서의 개념을 사용해 설명하시오.

강사 운영 노트

시점주의사항
배치 위치D1(파일시스템) 직후, D2(권한·스트림) 이전에 배치하는 것을 권장합니다. D1의 "명령어 사용"과 D2의 "왜 안전한가"를 이론으로 이어주는 다리 역할입니다.
strace 설치WSL Ubuntu 기본 이미지에는 strace가 없는 경우가 많습니다. 실습 시작 전 sudo apt install -y strace를 전원이 먼저 실행하도록 안내하십시오.
속도 조절비전공자에게 커널/사용자 모드 구분은 처음엔 추상적입니다. 2교시 이론 직후 바로 실습 A-3(strace)으로 넘어가 "눈으로 보여주는" 순서를 지키면 이해도가 크게 오릅니다.
깊이 조절시스템 콜 번호, 커널 소스코드 수준까지 들어갈 필요는 없습니다. "무엇을, 왜 커널에 요청하는가"라는 개념적 이해가 목표선입니다.
연결 강조이 문서의 fork/exec 개념은 D4 프로세스 수업, strace의 open/read/write는 D3 텍스트 처리(파일 스트림)와 반드시 연결지어 상기시켜 주십시오.
