Git 왕초보 실습 가이드 — 저장소 만들기부터 브랜치 병합까지

하나의 작은 프로젝트를 처음부터 끝까지 직접 관리해보며, Git의 전체 흐름을 손으로 익힙니다

이 문서는 D6 본문(06.html)보다 훨씬 쉬운 말로, 하나의 이야기를 따라가듯 Git을 처음부터 끝까지 체험하는 실습 가이드입니다. 용어를 몰라도 괜찮습니다. 순서대로 따라 치기만 하면 됩니다.

Git이 뭔가요? 아주 쉬운 비유부터

Git은 "되돌리기 버튼이 달린 일기장"이라고 생각하면 됩니다.

  • 보통 파일은 저장할 때마다 이전 내용을 덮어씁니다. 어제 쓴 내용이 뭐였는지 알 방법이 없습니다.
  • Git으로 관리하는 폴더는 "저장할 때마다" 그 순간의 스냅샷(사진)을 별도로 남깁니다.
  • 그래서 나중에 "3일 전 상태로 돌아가고 싶다", "누가 언제 이 부분을 고쳤는지 보고 싶다"가 전부 가능해집니다.

게임으로 치면 "저장 포인트"이고, 사진으로 치면 "앨범에 꽂아둔 사진 한 장 한 장"입니다. 그 저장 포인트 하나하나를 Git에서는 커밋(commit)이라고 부릅니다.

오늘 만들 것

거창한 프로젝트가 아니라, 내가 리눅스 수업에서 배운 걸 정리하는 학습 노트 폴더를 만들고, 그걸 Git으로 관리해보겠습니다. 실무에서도 딱 이 흐름 그대로, 폴더 하나 → 파일 몇 개 → 저장 → 수정 → 저장을 무한 반복합니다.

STEP 0. 준비물 확인과 최초 설정

Git이 설치되어 있는지 먼저 확인하고, "이 컴퓨터에서 커밋할 때 내 이름을 이렇게 남길게"라고 딱 한 번만 알려줍니다.

$ git --version
git version 2.43.0

$ git config --global user.name "내이름"
$ git config --global user.email "my-email@example.com"

$ git config --global -l
user.name=내이름
user.email=my-email@example.com

설명: --global은 "이 컴퓨터 전체에서 항상 이 이름을 쓰겠다"는 뜻입니다. 편지 봉투에 항상 같은 보내는 사람 이름을 쓰는 것과 같아서, 한 번만 설정해두면 앞으로 만드는 모든 저장소에 자동으로 적용됩니다. 이 단계는 컴퓨터 하나당 딱 한 번만 하면 됩니다.

STEP 1. 저장소 시작하기 — git init

일기장을 쓰기 전에 먼저 "이 폴더는 이제부터 Git이 관리하는 폴더"라고 선언해야 합니다.

$ mkdir -p ~/kdt-linux/my-notes
$ cd ~/kdt-linux/my-notes
$ git init
Initialized empty Git repository in /home/kdt/kdt-linux/my-notes/.git/

설명: git init은 지금 있는 폴더 안에 .git이라는 보이지 않는 폴더를 하나 만듭니다. 이 .git 폴더 안에 앞으로의 모든 저장 기록(커밋 이력)이 차곡차곡 쌓입니다. 이 폴더가 생기는 순간부터 이 자리는 더 이상 평범한 폴더가 아니라 "Git 저장소"가 됩니다. 처음이자 마지막으로 딱 한 번만 실행합니다.

STEP 2. 첫 파일 만들고 상태 보기 — git status

$ echo "# 리눅스 학습 노트" > notes.md
$ echo "오늘 배운 것: cd, ls, mkdir" >> notes.md

$ git status
On branch main

No commits yet

Untracked files:
  (use "git add ..." to include in what will be committed)
        notes.md

nothing added to commit but untracked files present (use "git add" to track)

설명: git status는 "지금 이 폴더 상태가 어떤지" 알려주는, Git에서 가장 자주 쓰는 명령입니다. Untracked files는 "이 파일은 아직 Git에게 소개된 적이 없다"는 뜻입니다. 방금 만든 notes.md가 아직 Git의 관리 대상이 아니라는 걸 알려주는 겁니다.

습관 팁: 뭔가 헷갈릴 때는 일단 git status부터 치세요. 지금 상황이 무엇인지 항상 알려줍니다.

STEP 3. 포스트잇 붙이기 — git add

사진을 찍기 전에 "이번 사진에는 이 사람 저 사람을 넣을게"라고 정하듯이, 이번 저장(커밋)에 어떤 파일을 포함시킬지 먼저 골라야 합니다. 이 과정을 스테이징(staging)이라고 부릅니다.

$ git add notes.md

$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached ..." to unstage)
        new file:   notes.md

설명: git add 파일명은 그 파일에 "이번 커밋에 넣을 포스트잇"을 붙이는 것과 같습니다. git status를 다시 확인해보면 Untracked였던 파일이 Changes to be committed(커밋될 예정)로 바뀐 것을 볼 수 있습니다. 아직 저장(커밋)된 건 아니고, "저장 대기 상태"일 뿐입니다.

STEP 4. 도장 찍기 — git commit

포스트잇을 붙인 내용을 이제 진짜로 "저장 포인트"로 확정합니다. 이 순간부터는 되돌아올 수 있는 지점이 하나 생깁니다.

$ git commit -m "첫 학습 노트 작성"
[main (root-commit) 3f4a1c2] 첫 학습 노트 작성
 1 file changed, 2 insertions(+)
 create mode 100644 notes.md

설명: -m "메시지"는 "이 저장 포인트에 어떤 이름표를 붙일지"입니다. 나중에 이력을 볼 때 이 메시지만 보고도 "아, 이때 이런 작업을 했었지"를 알 수 있어야 하므로, 짧더라도 내용이 드러나게 쓰는 것이 좋습니다. 3f4a1c2 같은 문자열은 이 커밋의 고유한 이름표(해시)입니다 — 사람으로 치면 주민등록번호 같은 겁니다.

정리: 지금까지 수정 → add(포스트잇) → commit(도장) 3단계를 한 번 완주했습니다. 이 3단계가 Git 사용의 99%를 차지합니다. 앞으로는 이 3단계를 계속 반복할 뿐입니다.

STEP 5. 목차 확인하기 — git log

$ git log
commit 3f4a1c2d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b (HEAD -> main)
Author: 내이름 
Date:   Wed Sep 2 10:00:00 2026 +0900

    첫 학습 노트 작성

설명: git log는 지금까지 찍은 모든 도장(커밋)을 최신순으로 보여주는, 말 그대로 일기장 목차입니다. 지금은 1개뿐이지만 앞으로 계속 쌓이게 됩니다. 목록이 길어지면 git log --oneline으로 한 줄씩 간단히 볼 수 있습니다.

$ git log --oneline
3f4a1c2 첫 학습 노트 작성

STEP 6. 수정하고 무엇이 바뀌었는지 보기 — git diff

이제 노트에 내용을 좀 더 추가해보겠습니다.

$ echo "오늘 배운 것: grep, sed, awk" >> notes.md

$ git diff
diff --git a/notes.md b/notes.md
index a1b2c3d..e4f5g6h 100644
--- a/notes.md
+++ b/notes.md
@@ -1,2 +1,3 @@
 # 리눅스 학습 노트
 오늘 배운 것: cd, ls, mkdir
+오늘 배운 것: grep, sed, awk

설명: git diff는 "마지막 저장(커밋) 이후로 무엇이 달라졌는지"를 보여줍니다. +로 시작하는 줄은 새로 추가된 내용이고, -로 시작하는 줄이 있다면 그건 지워진 내용입니다. 커밋하기 전에 "내가 뭘 바꿨더라?"를 확인하는 습관은 아주 중요합니다.

STEP 7. 두 번째 도장 찍기

STEP 3, 4에서 했던 add → commit을 그대로 한 번 더 반복합니다.

$ git add notes.md
$ git commit -m "grep, sed, awk 학습 내용 추가"
[main 7b8c9d0] grep, sed, awk 학습 내용 추가
 1 file changed, 1 insertion(+)

$ git log --oneline
7b8c9d0 grep, sed, awk 학습 내용 추가
3f4a1c2 첫 학습 노트 작성

설명: 이제 저장 포인트가 2개로 늘었습니다. 이렇게 "조금 고치고 저장, 조금 고치고 저장"을 반복하는 것이 Git을 쓰는 일상입니다. 한 번에 너무 많은 내용을 몰아서 커밋하지 말고, 의미 있는 작업 단위마다 자주 커밋하는 것이 좋은 습관입니다.

STEP 8. 실수 되돌리기 — git restore

이번엔 일부러 실수를 내보겠습니다.

$ echo "asdfasdf 실수로 아무거나 입력함" >> notes.md
$ cat notes.md
# 리눅스 학습 노트
오늘 배운 것: cd, ls, mkdir
오늘 배운 것: grep, sed, awk
asdfasdf 실수로 아무거나 입력함

$ git restore notes.md

$ cat notes.md
# 리눅스 학습 노트
오늘 배운 것: cd, ls, mkdir
오늘 배운 것: grep, sed, awk

설명: git restore 파일명은 "이 파일을 마지막으로 저장(커밋)했던 상태로 되돌려줘"라는 명령입니다. 아직 add도 안 하고 commit도 안 한, 즉 저장하기 전의 실수라면 이렇게 깔끔하게 취소할 수 있습니다. 이래서 자주 커밋해두는 것이 좋습니다 — 커밋해둔 지점까지는 언제든 안전하게 돌아갈 수 있으니까요.

STEP 9. 보기 싫은 파일 숨기기 — .gitignore

노트를 정리하다 보면 임시 파일이나, Git에 올리고 싶지 않은 파일이 생길 수 있습니다.

$ touch temp_draft.tmp
$ git status
Untracked files:
        temp_draft.tmp

$ echo "*.tmp" > .gitignore
$ git status
Untracked files:
        .gitignore

설명: .gitignore라는 이름의 파일 안에 패턴을 적어두면, Git이 그 패턴에 맞는 파일을 아예 목록에서 빼줍니다. 위에서는 *.tmp(확장자가 tmp인 모든 파일)를 무시하도록 지정했더니, temp_draft.tmp가 git status에서 더 이상 보이지 않게 되었습니다. 반면 .gitignore 파일 자신은 새로 생긴 파일이니 그대로 add/commit해서 남겨두면 됩니다.

$ git add .gitignore
$ git commit -m "임시 파일 무시 설정 추가"

STEP 10. 실험용 노트 만들기 — git branch

이번엔 "원본은 안전하게 두고, 새로운 실험을 해보고 싶다"는 상황을 만들어보겠습니다. 이럴 때 쓰는 것이 브랜치(branch)입니다 — 원본 노트를 복사해서 낙서장을 하나 더 만드는 것과 비슷합니다.

$ git branch
* main

$ git switch -c git-정리
Switched to a new branch 'git-정리'

$ git branch
  main
* git-정리

설명: git branch는 지금 있는 갈래(브랜치) 목록을 보여줍니다. *가 붙은 것이 지금 내가 있는 곳입니다. git switch -c 새이름은 "새 브랜치를 만들면서 동시에 그리로 이동"하는 명령입니다. 지금 main이라는 원본 노트는 그대로 두고, git-정리라는 복사본 노트로 넘어온 상태입니다. 여기서 무슨 짓을 해도 main은 전혀 영향받지 않습니다.

STEP 11. 실험 노트에서 작업하고 저장하기

$ echo "오늘 배운 것: git init, add, commit" >> notes.md
$ git add notes.md
$ git commit -m "git 기초 명령어 정리 추가"
[git-정리 a1b2c3d] git 기초 명령어 정리 추가

설명: 지금까지와 똑같은 add → commit입니다. 다른 점은, 이 커밋이 main이 아니라 git-정리라는 브랜치에만 기록된다는 것입니다. 지금 main 브랜치로 가서 notes.md를 열어보면 방금 추가한 줄이 보이지 않습니다 — 서로 다른 노트니까요.

STEP 12. 성공한 실험을 원본에 합치기 — git merge

실험이 마음에 들었으니, 이제 원본 노트에 이 내용을 반영해보겠습니다.

$ git switch main
Switched to branch 'main'

$ cat notes.md
# 리눅스 학습 노트
오늘 배운 것: cd, ls, mkdir
오늘 배운 것: grep, sed, awk
(git-정리 브랜치에서 추가한 줄은 아직 안 보임)

$ git merge git-정리
Updating 7b8c9d0..a1b2c3d
Fast-forward
 notes.md | 1 +
 1 file changed, 1 insertion(+)

$ cat notes.md
# 리눅스 학습 노트
오늘 배운 것: cd, ls, mkdir
오늘 배운 것: grep, sed, awk
오늘 배운 것: git init, add, commit

설명: git switch main으로 먼저 원본 노트로 돌아온 다음, git merge 브랜치이름으로 "저 브랜치에서 있었던 변경사항을 지금 여기(main)로 가져와서 합쳐줘"라고 지시합니다. 합치기가 끝나면 main에도 그 내용이 반영됩니다. 이제 실험이 끝났으니 다 쓴 실험 노트는 정리해도 됩니다.

$ git branch -d git-정리
Deleted branch git-정리 (was a1b2c3d).

STEP 13. 두 사람이 같은 줄을 고치면? — 충돌

브랜치를 나눠서 작업하다 보면, 원본과 실험 노트에서 같은 줄을 서로 다르게 고치는 경우가 생깁니다. 이럴 때 Git은 "둘 중 뭐가 맞는지 몰라서" 자동으로 합치지 못하고 사람에게 물어봅니다. 아주 간단한 상황으로 직접 체험해보겠습니다.

# main에서 첫 줄을 수정
$ echo "# 나의 리눅스 학습 노트 (완성본)" > notes.md
$ git commit -am "제목을 완성본으로 수정"

# 실험 브랜치를 하나 새로 만들어서, main과 다르게 첫 줄을 수정
$ git switch -c 제목변경-실험
$ echo "# 리눅스 정리노트 (버전2)" > notes.md
$ git commit -am "제목을 버전2로 수정"

$ git switch main
$ git merge 제목변경-실험
Auto-merging notes.md
CONFLICT (content): Merge conflict in notes.md
Automatic merge failed; fix conflicts and then commit the result.

설명: 두 브랜치가 같은 첫 줄을 서로 다르게 고쳤기 때문에 CONFLICT(충돌)이 발생했습니다. 당황할 필요 없습니다. 파일을 열어보면 아래처럼 양쪽 내용이 표시(마커)와 함께 남아 있습니다.

$ cat notes.md
<<<<<<< HEAD
# 나의 리눅스 학습 노트 (완성본)
=======
# 리눅스 정리노트 (버전2)
>>>>>>> 제목변경-실험
오늘 배운 것: cd, ls, mkdir
...

설명: <<<<<<< HEAD부터 =======까지는 "지금 내가 있던 쪽(main)"의 내용이고, =======부터 >>>>>>>까지는 "합치려던 쪽(실험 브랜치)"의 내용입니다. 이걸 사람이 직접 보고, 어느 쪽을 남길지(혹은 둘을 합쳐 새로 쓸지) 정한 뒤 마커 기호는 전부 지우고 원하는 최종 내용만 남기면 됩니다.

# 에디터로 열어서 마커를 지우고 원하는 제목만 남긴다
$ nano notes.md
# (예: "# 나의 리눅스 학습 노트 (완성본)" 한 줄만 남기고 저장)

$ git add notes.md
$ git commit -m "제목 충돌 해결 — 완성본으로 통일"
[main 5e6f7a8] 제목 충돌 해결 — 완성본으로 통일

설명: 충돌 마커를 지우고 원하는 내용으로 정리한 뒤 add하면, Git에게 "이제 이 파일은 정리 끝났어"라고 알리는 것입니다. 그다음 commit을 하면(이번엔 메시지를 직접 적어줘야 합니다) 충돌 해결이 완료됩니다.

$ git branch -d 제목변경-실험

겁먹지 마세요: 충돌은 Git이 고장난 게 아니라, "너 이거 사람이 직접 확인해야 할 것 같아"라고 정직하게 알려주는 것뿐입니다. 팀 프로젝트(교과 14·15)에서도 자주 만나는 아주 정상적인 상황입니다.

STEP 14. 완성본에 이름표 붙이기 — git tag

중요한 시점(예: 제출본, 완성본)에는 나중에 쉽게 찾을 수 있도록 이름표를 붙여둘 수 있습니다.

$ git tag v1.0
$ git tag
v1.0

$ git log --oneline
5e6f7a8 (HEAD -> main, tag: v1.0) 제목 충돌 해결 — 완성본으로 통일
...

설명: git tag 이름은 지금 이 커밋에 책갈피를 꽂아두는 것과 같습니다. 나중에 커밋이 수백 개로 늘어나도, v1.0이라는 이름표만 기억하면 그 지점을 바로 찾아갈 수 있습니다.

전체 흐름 한눈에 보기

[작업 폴더]          [스테이징]           [저장소(.git)]
notes.md 수정   --add-->  포스트잇 붙음  --commit-->  저장 포인트 생성
     ↑                                                    │
     └──────────────────── restore ──────────────────────┘
                       (커밋 전이라면 여기로 되돌릴 수 있음)

[main]  ──switch -c──▶ [실험 브랜치]
   ▲                         │
   └────────merge───────────┘
      (실험이 성공하면 다시 합침, 충돌나면 사람이 직접 정리)

오늘 한 것을 말로 풀면 이렇습니다: "폴더를 Git 저장소로 만들고(init) → 파일을 고칠 때마다 add·commit을 반복하고 → 필요하면 브랜치로 안전하게 실험하고 → merge로 다시 합치고 → 중요한 지점엔 tag를 붙인다." 이 흐름이 Git 사용의 전부입니다. D6 본문(06.html)에서는 이 각각을 조금 더 깊이 있게, 팀 프로젝트 규칙과 함께 다룹니다.
